# BinkP Protocol

- **binkd EOB batching**: binkd does not close a session after the first bidirectional M_EOB exchange if that batch carried more than 2 protocol messages (true of almost any real transfer). It silently starts a second, normally-empty batch, sends a fresh M_EOB for it, and only closes once it receives a reply M_EOB for that batch too. `BinkpSession` must always reply to an incoming M_EOB (never terminate directly on receiving one) and drive termination primarily off the peer closing the connection, not off completing one EOB round-trip — closing early causes binkd to log an otherwise-successful session as `failed`. See `docs/UPGRADING_1.10.0.md` ("BinkP Session Close Could Be Reported as a Failed Session by Remote Mailers") for the full history; fixed in commit `ee4c4601`.
- `BinkpSession::close()` shuts the write side down and briefly drains any trailing bytes before the final `fclose()`, rather than closing immediately — necessary but not sufficient on its own for the EOB batching issue above.
- **Symmetric-peer EOB ping-pong**: because we always reply to an incoming M_EOB (see above), two nodes that are *both* running this same policy — e.g. two BinktermPHP installs talking to each other, as opposed to one side being a real binkd — will otherwise bounce M_EOB back and forth indefinitely, since each side's reply is itself a fresh incoming M_EOB for the other side to reply to. `BinkpSession::$eobRepliesSent` caps our own auto-replies at `MAX_EOB_AUTO_REPLIES` (2) per session to break that cycle; a real binkd peer never needs more than two replies from us (its real batch, then its one normally-empty follow-up batch), so the cap is transparent to normal binkd interop. Surfaced via `scripts/freq_getfile.php` hanging for the full session timeout when FREQing another BinktermPHP node.
- Set `BINKP_LOG_LEVEL=DEBUG` in `.env` to get verbose protocol logging from `binkp_server.php`, `binkp_poll.php`, and `binkp_scheduler.php` without changing how those processes are launched (useful since they normally run under systemd/cron with no `--log-level` flag).
