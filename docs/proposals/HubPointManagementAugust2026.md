## Overview

`docs/proposals/HubPointSystemJuly2026.md` (implemented, branch `hubpoint`) built the sysop-facing side of hub/point distribution: `hub_nodes`, echomail/netmail/TIC fanout, binkp push/pull delivery, and the Areafix/FileFix netmail robots. Its **Out of Scope** section explicitly named self-service point provisioning as a future extension:

> **Automatic point provisioning from user accounts** — points are registered by the sysop via the admin UI in this phase; self-service "request a point" flows are a possible future extension, not part of this proposal.

and its **Open Questions** section asked:

> Should points have web UI account access in addition to BinkP, or BinkP-only?

This proposal answers both: it adds a permission-gated, self-serve "Point Management" page that lets an authorized local user create and manage their own point registration in `hub_nodes` — including its echoarea and filearea subscriptions — without giving them access to sysop-only settings (hub registration, inbound/outbound routing flags, point number reassignment).

## Goals

- A user with a new `manage_hub_point` flag on their account can request a point address for themselves without sysop intervention per-request.
- A `hub_nodes` row can be associated with the local user who owns it, so the self-serve page and the admin UI both know which row belongs to which account.
- Users may self-register up to a configurable number of points per network (per boss AKA); they cannot create hubs (node-type `hub_nodes` rows) for themselves under any circumstance.
- The set of fields a point owner can edit themselves is small and safe: session/packet password, Areafix/FileFix passwords, Internet host and port, hold mail, compress outbound, and their echoarea/filearea subscriptions. Everything else (point number, boss address, enable/disable, inbound/outbound allow flags) stays sysop-only.
- The admin Downlinks manager gains a user-association selector so a sysop can link an existing or newly-created `hub_nodes` row to a local account, including rows created through this self-serve flow.

## Non-Goals

- No self-service hub/node registration — a user can never register an address that is not a point of one of the system's own AKAs.
- No self-service point-number selection — the point number is assigned by the same allocation logic the admin UI already uses (`HubNodeManager`'s next-point-number lookup), not user-chosen.
- No changes to the Areafix/FileFix netmail robots themselves — they remain available as a netmail-based alternative for subscription management (e.g. from an offline mail reader), operating on the same `hub_node_areas`/`hub_node_fileareas` rows as the web page. This proposal adds a second, web-based way to manage the same data, not a replacement for the robots.

## Permission Model

### `manage_hub_point` user flag

`users` currently has no generic permissions/roles table — access control today is the single `users.is_admin` boolean (`src/Auth.php`) plus `License::isValid()` for premium gating. This feature needs a narrower grant than "admin" (a sysop may want to authorize a specific trusted user without making them a full admin) and it is not a premium/license feature, so it needs its own column rather than overloading either mechanism.

Add a new boolean column, `users.manage_hub_point` (default `false`), via a standard migration (see `/new-migration`). A user may access the self-serve Point Management page and its API only when `manage_hub_point = true` OR `is_admin = true` (an admin implicitly has the grant, consistent with how admin-gated features already treat admins as a superset).

The flag itself is set by the sysop from the existing user administration screen (wherever `is_admin` and similar per-user toggles are currently exposed) — this proposal adds the flag and its enforcement, not a new user-editing surface, so the toggle should be added next to `is_admin` in the existing admin user edit form.

Revoking `manage_hub_point` from a user does not touch any point they already created — the `hub_nodes` row, its enabled state, and its mail flow are unaffected. It only removes the user's ability to reach the self-serve Point Management page and its API for that row going forward. If the sysop wants the point itself disabled or removed after revoking the flag, that is a separate, manual action taken through the existing admin Downlinks UI, same as for any other point.

## Data Model Changes

### `hub_nodes.user_id`

Add a nullable `user_id INTEGER NULL REFERENCES users(id)` column to `hub_nodes`. `NULL` for hub/node rows and for points the sysop registers without linking to an account (unchanged behavior for all existing rows). Set for a point row that is either:

- created through the self-serve flow (always set to the creating user), or
- linked after the fact by a sysop through the new admin selector, for a point the sysop registered manually on the user's behalf.

A `hub_nodes` row's `user_id` is informational/ownership metadata for the self-serve and admin UIs; it does not change fanout, delivery, or routing logic in `HubFanout`, `HubNetmailRouter`, or `HubAreafixProcessor`, none of which need to know about it.

### One point per network per user — self-service only, configurable

"One point per network" means one point per boss AKA, since a network in this codebase is identified by which of the system's own AKAs a point hangs off (`hub_nodes.boss_address`). This limit applies to the **self-serve creation path only** — the sysop may still associate additional points under the same boss AKA with a user via the admin selector (e.g. provisioning a second point on the user's behalf), so it cannot be a blanket database constraint on `(user_id, boss_address)`.

The limit itself is a configurable count, not a hardcoded `1`, read via `Config::env('HUB_POINT_MAX_PER_USER_PER_NETWORK', '1')` per the project's convention of sourcing application config through `Config::env()`. Default is `1` (matching the requirement as stated); a sysop who wants to allow users to self-register more than one point per network can raise it in `.env`. A value of `0` or less should be treated as "self-service disabled" (reject every self-serve creation request) rather than "unlimited," since an unbounded self-serve limit was never a requirement and silently allowing it would be surprising.

Enforce it in `POST /api/point-management`: before inserting, count existing rows with `node_type='point'`, `user_id = <requester>`, and `boss_address = <requested boss AKA>`, and reject the request with a translated `errors.*` key if the count is already at or above the configured limit. Guard the check-then-insert race with a transaction (`SELECT ... FOR UPDATE` against the user's existing point rows scoped to that boss address, or an application-level advisory lock keyed on `(user_id, boss_address)`) rather than relying on a unique index, since a fixed unique index would both hardcode the limit back to 1 and incorrectly block legitimate sysop-assigned extra points.

Document the new variable in `docs/CONFIGURATION.md` alongside the other `.env` settings when this is implemented, per the project's convention of documenting env-driven behavior toggles there (see the removed `HUB_ROUTE_NETMAIL` entry in `HubPointSystemJuly2026.md` for precedent on how such flags are documented and later retired).

## Admin UI: User Association Selector

`templates/admin/hub_nodes.twig`'s add/edit modal gains a user-association field, alongside the existing fields (mirrors the general shape of `templates/admin/networks.twig`'s per-uplink form). Requirements:

- Free-form text input with autocomplete against local usernames, not a `<select>` populated with every user — the user base can be large enough that a full dropdown is impractical, and the sysop usually knows the username they're looking for.
- Autocomplete queries a new lightweight endpoint, e.g. `GET /admin/api/users/autocomplete?q=<partial>`, returning `{id, username}` matches (reuse an existing user-search endpoint if one already exists elsewhere in the admin UI rather than adding a duplicate).
- Selecting a suggestion stores the user's `id` in a hidden field submitted as `user_id`; clearing the text field clears the association (submits `user_id: null`).
- The field is optional on both create and edit — hub/node rows simply leave it blank, and existing points remain unassociated until a sysop links them.
- If the entered username doesn't resolve to an autocomplete selection, the field should not silently save a bogus association — validate server-side that `user_id`, if provided, corresponds to an existing user, and reject the request with a translated `errors.*` key otherwise.
- The admin API's create/update handlers for `/admin/api/hub-nodes` need to accept and persist `user_id`, and the existing `HubNodeManager::isValidFtnAddress()`/create/update methods need a `user_id` parameter threaded through.

## User-Facing "Point Management" Page

### Placement

A new entry in the logged-in user's dropdown menu, labeled "Point Management", visible only when the current user has the `manage_hub_point` grant (flag or admin). Per `templates/CLAUDE.md`, the menu item must be added identically to `templates/base.twig`, `templates/shells/web/base.twig`, and `templates/shells/bbs-menu/base.twig`. The page itself lives under the normal authenticated web UI (not `/admin`), e.g. `/point-management`, and its route handler enforces the grant server-side — the menu item being hidden is a convenience, not the access control.

### No existing point: request flow

If the current user has no associated `hub_nodes` point row, the page shows a single "Create Point Address" action instead of a management form. Creating a point:

1. User selects which of the system's own AKAs/networks to request a point under, from the list of networks that currently have at least one enabled boss AKA available for point creation (mirrors however the admin add-point flow currently sources that list).
2. Server allocates the next point number for that boss address using the same logic the admin UI's point-creation path already uses, generates a random `session_password`/`packet_password` (shown once, with a copy-to-clipboard affordance, matching how other generated-secret flows in the codebase surface one-time secrets), and inserts the `hub_nodes` row with `node_type='point'`, `user_id` set to the requester, and defaults matching what the admin UI defaults a new point to (enabled, `allow_inbound`/`allow_outbound` true, `hold_mail` false, `compress_outbound` per system default).
3. The application-level check in [Data Model Changes](#data-model-changes) rejects a second self-serve request under the same boss address for the same user; the API surfaces this as a translated error rather than a generic failure.
4. The sysop is not required to approve each individual point creation — the `manage_hub_point` grant itself is the approval step. The sysop is notified after the fact instead: point creation must trigger the existing admin notification mechanism (whatever it already uses for comparable sysop-facing events) so the sysop is aware a new point was self-provisioned, including the requesting username, the boss AKA/network, and the assigned point address.

### Existing point(s): management flow

With the default limit of 1, the page shows a single point's details once the user has one. Because the limit is configurable, the page must still handle the case where a sysop has raised `HUB_POINT_MAX_PER_USER_PER_NETWORK` above 1 and the user holds more than one self-registered point (across different networks, or the same network if the sysop raised the per-network cap): show a list of the user's points (one row per `hub_nodes` entry with that `user_id`, self-registered or sysop-assigned alike — the page does not distinguish by origin once a point is associated with the user) and let them open one at a time for editing, rather than assuming a single record. `GET /api/point-management` should therefore return an array, not a single nullable object, even though the default configuration and the common case is a one-element (or empty) array.

Each point's detail view shows its read-only identity (`node_address`, boss address, point number — matching the "point number is sysop-only" rule) plus an edit form limited to:

| Field | Editable by point owner |
|---|---|
| `node_address`, `point_number`, `boss_address` | No — read-only display |
| `session_password`, `packet_password` | Yes — regenerate or set directly |
| `areafix_password`, `filefix_password` | Yes |
| `inet_host`, `port` | Yes |
| `hold_mail` | Yes (toggle) |
| `compress_outbound` | Yes (toggle) |
| `enabled` | No |
| `allow_inbound`, `allow_outbound`, `allow_inbound_echomail`, `allow_inbound_netmail` | No |
| `max_packet_kb`, `queue_retention_days`, `capability_flags` | No |
| Echoarea/filearea subscriptions (`hub_node_areas`/`hub_node_fileareas`) | Yes — see [Subscription Management](#subscription-management) |

The API endpoint backing this form (e.g. `PUT /api/point-management/{id}`) must independently enforce this column allowlist server-side — it must not simply forward the whole request body to `HubNodeManager`'s update method, since that method is also used by the unrestricted admin path. The cleanest approach is a dedicated `HubNodeManager::updateSelfServeFields(int $hubNodeId, int $ownerId, array $fields)` that whitelists exactly the rows in the table above (excluding subscriptions, which go through their own endpoint — see below) and verifies `$ownerId` matches the row's `user_id` before writing anything.

### Subscription Management

The point owner can subscribe/unsubscribe their point to/from echoareas and fileareas directly from the Point Management page, functionally equivalent to what the admin's per-downlink subscription checklist modals in `templates/admin/hub_nodes.twig` already do, and to what the Areafix/FileFix netmail robots already do for a subordinate managing itself remotely — this page is a third way to reach the same `hub_node_areas`/`hub_node_fileareas` rows, not a new subscription model.

- **Eligible areas are restricted** the same way `HubAreafixProcessor` already restricts self-subscribable areas: active, non-local echoareas excluding sysop-only, and active, non-local, non-private fileareas. A point owner must not be able to subscribe to an area through the web page that they couldn't subscribe to via `+TAG` over netmail.
- The UI presents a checklist per area type (mirroring the admin modal's shape), scoped to the one point being edited.
- New endpoints, scoped and permission-checked the same as the rest of this API surface:
  - `GET /api/point-management/{id}/areas` / `PUT /api/point-management/{id}/areas` — echoarea subscription list/update.
  - `GET /api/point-management/{id}/fileareas` / `PUT /api/point-management/{id}/fileareas` — filearea subscription list/update.
  - These should share their eligibility-filtering and persistence logic with `HubAreafixProcessor` and the existing admin `/admin/api/hub-nodes/{id}/areas`/`/fileareas` handlers rather than reimplementing area lookups a third time — factor the eligible-area query into a shared method on `HubNodeManager` (or wherever `HubAreafixProcessor` currently sources its eligibility list) if it isn't already centralized, per the project's "avoid duplicating code" convention.
- Subscribing/unsubscribing here does not itself queue a historical resend the way `%RESCAN` does for Areafix — a newly-subscribed area starts receiving mail going forward only. If the user wants area history, they still need to ask the sysop or use `%RESCAN` over netmail (out of scope for this proposal's web UI, consistent with [Non-Goals](#non-goals) not touching robot behavior).

### Deletion

The point owner may delete any of their own point registrations from this page. Deletion should use `HubNodeManager`'s existing delete path (the same one the admin UI uses), scoped to rows where `user_id` matches the requesting user — a self-serve delete must never be able to target a row it doesn't own. Existing queued outbound mail (`hub_node_outbound`) and area subscriptions (`hub_node_areas`/`hub_node_fileareas`) for the row follow whatever cascade/cleanup behavior the admin delete path already implements; this proposal does not change that behavior.

## API Surface

New endpoints, all requiring the `manage_hub_point` grant (flag or admin) and all scoped to rows where `user_id` matches the requesting user:

- `GET /api/point-management` — returns an array of the current user's point rows (empty array if they have none — see [Existing point(s): management flow](#existing-points-management-flow) for why this is a list rather than a single nullable object).
- `GET /api/point-management/networks` — lists boss AKAs available for point creation.
- `POST /api/point-management` — creates a point under a chosen boss AKA (fails once the user has reached `HUB_POINT_MAX_PER_USER_PER_NETWORK` self-registered points for that boss address).
- `PUT /api/point-management/{id}` — updates the self-serve field subset for one of the user's existing points; 403/404 if `{id}` doesn't belong to the requester.
- `DELETE /api/point-management/{id}` — deletes one of the user's point registrations; 403/404 if `{id}` doesn't belong to the requester.
- `GET /api/point-management/{id}/areas` / `PUT /api/point-management/{id}/areas` — echoarea subscription list/update for one of the user's points (see [Subscription Management](#subscription-management)).
- `GET /api/point-management/{id}/fileareas` / `PUT /api/point-management/{id}/fileareas` — filearea subscription list/update for one of the user's points.

Extend `routes/admin-routes.php`'s existing `/admin/api/hub-nodes*` handlers to accept/return `user_id`, and add `GET /admin/api/users/autocomplete` (or reuse an existing equivalent) for the admin selector.

## i18n

All new UI text (menu item label, page headings, form labels, generated-password display, subscription checklist labels, error messages) needs `ui.*`/`errors.*` keys added to every locale directory under `config/i18n/`, per the project's i18n workflow — reuse the existing `ui.admin.hub_nodes.*` checklist strings where the self-serve checklist UI is functionally identical to the admin one, rather than duplicating equivalent English text under a new key namespace. New API errors (duplicate point request, editing a restricted field, deleting/updating a point the user doesn't own, subscribing to an ineligible area, invalid username in the admin autocomplete field) need `errors.*` keys returned as `error_code`, not raw strings.

## Address Parsing Note

The codebase currently has three near-duplicate FTN address parsers (`EchomailSeenBy::parseFtnAddressParts()`, a private copy in `BinkdProcessor`, and `NodelistManager::parseAddress()`), plus `HubNodeManager::isValidFtnAddress()` for format validation. This proposal's point-creation flow only needs to *compose* a `boss.point` address from an already-valid boss AKA and an allocated integer, not parse arbitrary input, so it does not need a new parser and should not add a fourth one. If implementation work here finds a genuine need for parsing, prefer consolidating into one shared utility rather than adding another copy, per the project's "avoid duplicating code" convention.

## Decisions

1. **One point per network, per user via self-service, configurable.** Default limit is 1 self-registered point per boss AKA per user, enforced in `POST /api/point-management` (see [One point per network per user — self-service only, configurable](#one-point-per-network-per-user--self-service-only-configurable)); overridable via `HUB_POINT_MAX_PER_USER_PER_NETWORK` in `.env`. It does not limit the sysop — the admin Downlinks UI's user-association selector may link additional points under the same or different boss AKAs to a user regardless of this limit, for cases like a sysop provisioning extra points on the user's behalf. The self-serve Point Management page only ever manages the point(s) the user themselves created via self-service, up to the configured cap; sysop-assigned extra points remain admin-managed only.
2. **Sysop notification on creation.** Every self-serve point creation notifies the sysop via the existing admin notification mechanism, including requester, network, and assigned address — see [User-Facing "Point Management" Page](#user-facing-point-management-page).
3. **Flag revocation does not touch the point.** Disabling `manage_hub_point` only removes the user's access to manage their existing point; the `hub_nodes` row stays exactly as it was (enabled, mail flowing) until a sysop manually disables or deletes it via the admin Downlinks UI.
4. **Mid-poll password rotation is acceptable.** No special handling is needed if a point owner changes `session_password`/`packet_password` while a binkp session involving that point is in flight; the next session simply authenticates with the new credentials.
