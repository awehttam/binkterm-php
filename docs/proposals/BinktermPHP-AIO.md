# BinktermPHP All-In-One Process Manager

> **Draft** — This proposal was generated by AI and may not have been reviewed for accuracy. It is intended as a starting point for discussion.

> **Status update:** `binktermphp-pm` and `binktermphp-ctl` are no longer built from this repository (`tools/binktermphp-pm/` and the `makego`/`binktermphp-pm.*` wrapper scripts described below have been removed). Development continues at [github.com/awehttam/binktermphp-pm](https://github.com/awehttam/binktermphp-pm). As of BinktermPHP 1.9.10, the web interface and admin daemon support driving the external process manager when `config/aio.json` is present, but this is still experimental — see [UPGRADING_1.9.10.md](../UPGRADING_1.9.10.md) — and there is no migration path from cron/systemd-based deployments yet. The architecture, service table, and configuration format below describe the design intent and may not exactly match the current external implementation.

## Objective

Provide a single process manager binary (`binktermphp-pm`) that starts, supervises, and restarts all BinktermPHP daemons, with health monitoring of external dependencies (Caddy, PostgreSQL). A companion control tool (`binktermphp-ctl`) lets the sysop start, stop, and restart individual services while the manager is running.

This is the **primary recommended deployment method** for BinktermPHP. The previous approaches — cron-based restarts and manually written systemd units — remain supported as alternatives but are no longer the recommended path.

Running `binktermphp-pm` with no arguments launches an interactive console showing live service status and log output. Passing `--daemon` detaches it to the background instead.

---

## Language: Go

PHP is ruled out — the project has had reliability problems with PHP supervising long-lived child processes. The recommended language is **Go**:

- Produces a single statically-linked binary with no runtime dependencies to install.
- Strong signal handling (SIGINT, SIGTERM, SIGHUP).
- `os/exec` gives direct control over child process lifecycle.
- Native Unix socket server for `binktermphp-ctl` IPC.
- Standard `log/slog` for structured logging.

Node.js is already present in the project but is not well-suited as a supervisor: its single-threaded event loop makes signal handling tricky, and it adds a second runtime dependency. Go compiles to a single file that can be committed as a release artifact or built from source with one command.

## Architecture Overview

```
binktermphp-pm (supervisor process)
├── reads  config/aio.json
├── spawns each enabled BinktermPHP daemon as a child process
├── tracks PID, status, uptime, restart count per service
├── auto-restarts crashed services with exponential back-off
├── health-checks external services (Caddy, PostgreSQL) on a polling interval
├── listens on data/run/binktermphp-pm.sock (Unix socket)
│   └── serves JSON-RPC commands from binktermphp-ctl
└── in console mode: renders a live status dashboard in the terminal
```

```
binktermphp-ctl <command> [service]
└── connects to data/run/binktermphp-pm.sock
    └── sends JSON-RPC command, prints response, exits
```

## Services

The following table covers all BinktermPHP daemons. All are launched in **foreground mode** (without `--daemon`) so the process manager owns the process directly — see [Foreground vs. Daemon Mode for Child Processes](#foreground-vs-daemon-mode-for-child-processes) below.

| Name | Command | Always-on | Restart Policy |
|---|---|---|---|
| `admin_daemon` | `php scripts/admin_daemon.php` | yes | always |
| `binkp_scheduler` | `php scripts/binkp_scheduler.php` | yes | always |
| `binkp_server` | `php scripts/binkp_server.php` | yes | always |
| `realtime_daemon` | `php scripts/realtime_server.php` | yes | always |
| `telnetd` | `php telnet/telnet_daemon.php` | no | on-failure |
| `ssh_daemon` | `php ssh/ssh_daemon.php` | no | on-failure |
| `mrc_daemon` | `php scripts/mrc_daemon.php` | no | on-failure |
| `gemini_daemon` | `php scripts/gemini_daemon.php` | no | on-failure |
| `ftp_daemon` | `php scripts/ftp_daemon.php` | no | on-failure |
| `mcp_server` | `node mcp-server/server.js` | no | on-failure |
| `multiplexing_server` | `node scripts/dosbox-bridge/multiplexing-server.js` | no | on-failure |
| `matterbridge_daemon` | `php scripts/matterbridge_daemon.php` | no | on-failure |

**Always-on** services are started unconditionally and restarted immediately if they exit. **Optional** services (marked `on-failure`) are started if `enabled: true` in `aio.json` and are only restarted if they exited with a non-zero status — a clean exit is treated as an intentional stop.

Caddy and PostgreSQL are **not** managed as child processes — see [External Service Health Monitoring](#external-service-health-monitoring) below.

## Foreground vs. Daemon Mode for Child Processes

All PHP daemons run in the foreground by default and only self-fork when `--daemon` is explicitly passed. The process manager launches them without `--daemon`, so it owns the process directly and can detect crashes, capture stdout/stderr, and enforce restart policies without any changes to the daemon scripts.

The `--daemon` / `--pid-file` path on each script remains intact for sysops who want to run daemons independently without the process manager. `scripts/restart_daemons.sh` is unaffected and continues to work alongside the process manager for manual interventions.

---

## External Service Health Monitoring

Caddy and PostgreSQL are installed and managed by the sysop (or the system package manager) — `binktermphp-pm` does not start or stop them. Instead, it polls each external service on the `health_check_interval_s` interval and reports their status in the dashboard and `binktermphp-ctl status` output alongside the managed daemons.

Two probe types are supported:

- **`tcp`** — opens a TCP connection to the given address. Used for PostgreSQL. Succeeds if the connection is accepted.
- **`http`** — issues a `GET` to the given URL and expects a 2xx response. Used for Caddy's admin API (`localhost:2019/healthz`).

Health check entries appear in the dashboard with a `health` badge rather than a PID, and have no restart controls. If a health check fails, the status shows `unreachable` and the failure is logged.

BinktermPHP will ship a **Caddy template** (`config/Caddyfile.example`) covering the recommended reverse-proxy configuration for the web interface.

## Console Mode (default)

When run without `--daemon`, `binktermphp-pm` renders a live terminal dashboard using ANSI escape codes:

```
BinktermPHP Process Manager  [q]uit  [s]tart  [S]top  [r]estart  [l]ogs

  SERVICE               TYPE     STATUS       PID      UPTIME     RESTARTS
  postgres              health   reachable    -        -          -
  caddy                 health   reachable    -        -          -
  admin_daemon          service  running      12301    2h 04m     0
  binkp_server          service  running      12302    2h 04m     0
  binkp_scheduler       service  running      12303    2h 04m     0
  realtime_daemon       service  running      12304    2h 04m     1
  telnetd               service  running      12305    1h 58m     0
  ssh_daemon            service  running      12306    1h 58m     0
  mrc_daemon            service  disabled     -        -          -
  gemini_daemon         service  disabled     -        -          -

  ── Logs (realtime_daemon) ──────────────────────────────────────────
  [14:32:01] WebSocket server listening on :8080
  [14:32:03] Client connected: 127.0.0.1
```

- Arrow keys select a service row; `l` tails its log output in the lower pane.
- `s` / `S` / `r` send start/stop/restart to the selected service (not available on health-check rows).
- `q` or Ctrl-C shuts down all managed services and exits.
- SIGHUP reloads `aio.json` and reconciles running services without a full restart.

Pressing Ctrl-Z or closing the terminal in console mode does **not** stop the managed services — the manager continues running detached. A subsequent `binktermphp-pm --attach` reconnects to the live dashboard.

## Daemon Mode (`--daemon`)

```
binktermphp-pm --daemon [--config config/aio.json] [--pid-file data/run/binktermphp-pm.pid]
```

- Double-forks, writes PID file, opens log file, closes stdin/stdout/stderr.
- Writes structured JSON log lines to `data/logs/binktermphp-pm.log` (configurable).
- Continues supervising all services in the background.
- `binktermphp-ctl status` shows current state.
- `binktermphp-ctl stop-all` terminates all children and the manager itself.

## `binktermphp-ctl`

`binktermphp-ctl` is a thin client binary (built from the same Go module) that connects to the manager's Unix socket and sends a JSON-RPC command.

```
binktermphp-ctl status                    # show status of all services and health checks
binktermphp-ctl status <service>          # show status of one service
binktermphp-ctl start <service>           # start a stopped service
binktermphp-ctl stop <service>            # stop a running service (SIGTERM, then SIGKILL)
binktermphp-ctl restart <service>         # stop then start
binktermphp-ctl reload                    # reload aio.json (SIGHUP equivalent)
binktermphp-ctl logs <service> [--tail N] # stream recent log lines
binktermphp-ctl stop-all                  # stop all services and the manager
```

If the socket does not exist (manager not running), `binktermphp-ctl` exits with a clear error message rather than hanging.

---

## IPC Protocol

Communication between `binktermphp-ctl` and `binktermphp-pm` uses newline-delimited JSON over a Unix domain socket. This is deliberately simple — no HTTP, no gRPC, no external dependencies.

**Request:**
```json
{ "id": "1", "method": "restart", "params": { "service": "binkp_server" } }
```

**Response:**
```json
{ "id": "1", "ok": true, "message": "binkp_server restarted (pid 14220)" }
```

**Error:**
```json
{ "id": "1", "ok": false, "error": "service 'binkp_server' is not enabled" }
```

Socket path defaults to `data/run/binktermphp-pm.sock` and is configurable in `aio.json`.

---

## Restart Policy and Back-off

| Policy | Behaviour |
|---|---|
| `always` | Restart on any exit (exit 0 or non-zero). |
| `on-failure` | Restart only on non-zero exit. A clean exit (code 0) is left stopped. |
| `never` | Never restart automatically. Only `binktermphp-ctl start` can bring it up. |

For any automatic restart, the manager applies **exponential back-off**: 1 s → 2 s → 4 s → … up to `restart_max_delay_s` (default 30 s). The delay resets to zero once a service has been healthy for 60 seconds. This prevents a crash-looping daemon from hammering the CPU.

---

## Signal Handling

| Signal | Effect on manager |
|---|---|
| SIGTERM / SIGINT | Graceful shutdown: SIGTERM all children, wait up to 10 s, SIGKILL survivors, exit. |
| SIGHUP | Reload `aio.json`; start newly-enabled services, stop removed ones, leave running services unchanged. |
| SIGUSR1 | Rotate log file (for logrotate integration). |

## Startup Order

Some services depend on others being up first (e.g., all PHP daemons need the database). A future revision can add explicit `depends_on` edges and readiness probes. For the initial implementation, services are started in the order they appear in `aio.json` with a configurable inter-service delay (default 250 ms). Health-check entries for `postgres` and `caddy` should be listed first in `aio.json` as a reminder to ensure they are up before the BinktermPHP daemons start.

## Build and Installation

```bash
# Build both binaries
cd tools/binktermphp-pm
go build -o ../../binktermphp-pm  ./cmd/pm
go build -o ../../binktermphp-ctl ./cmd/ctl

# Or via Makefile at the repo root
make aio
```

Binaries live at the repo root alongside `composer.json`. They are gitignored and built locally or in CI. Pre-built binaries will be published as GitHub release artifacts so sysops do not need a Go toolchain installed.

## Non-Goals

- **Windows support.** Unix signals and Unix sockets are used throughout. WSL2 is the supported path on Windows.
- **Remote management.** The IPC socket is local only. No HTTP API, no TLS, no authentication layer.
- **Service discovery or container orchestration.** This is a single-machine supervisor, not a cluster tool.
- **Managing the Caddy or PostgreSQL process lifecycle.** The PM monitors their health but does not start, stop, or restart them. Sysops who want full lifecycle control of those services should use their system's native tooling (systemd units, `pg_ctlcluster`, etc.).

## Phased Implementation

### Phase 1 — Process Manager (this document)

Deliver `binktermphp-pm` and `binktermphp-ctl` as described above. All BinktermPHP daemons are supervised. Caddy and PostgreSQL are health-monitored only. This becomes the primary recommended deployment method, replacing cron and systemd as the getting-started path.

Success criteria:
- All daemons start, restart on crash, and stop cleanly via `binktermphp-pm` and `binktermphp-ctl`.
- Console dashboard shows live status and log tail.
- Daemon mode is stable enough to run unattended on a production VPS.

### Phase 2 — FrankenPHP Integration

[FrankenPHP](https://frankenphp.dev) is a Go binary that embeds PHP and Caddy together. It replaces the separate web server (Caddy or Nginx) and PHP runtime (PHP-FPM or the built-in server) with a single process supervised by `binktermphp-pm`.

#### What Phase 2 delivers

- **Supervised FrankenPHP web server** — `frankenphp run --config config/Caddyfile` runs as a managed service with automatic restart on crash, identical to any other BinktermPHP daemon.
- **`config/Caddyfile.example`** — a ready-to-use template covering static assets, PHP routing via SimpleRouter (`php_server`), the BinkStream WebSocket reverse-proxy (`/ws → 127.0.0.1:6010`), compression, and security headers.
- **Automatic HTTPS** — FrankenPHP uses Caddy's built-in ACME client; no separate Certbot setup required.

#### What Phase 2 does not change

- Background PHP daemons (`admin_daemon`, `binkp_server`, etc.) continue to use the system `php` binary — FrankenPHP replaces the web server, not the CLI runtime.
- PostgreSQL remains external.
- The BinkStream WebSocket daemon (`realtime_daemon`) still runs as a separate supervised service.

#### Worker mode (future)

FrankenPHP can keep PHP warm between requests via a persistent worker process, eliminating per-request bootstrap overhead. This requires a dedicated `worker.php` entry point that calls `frankenphp_handle_request()` in a loop. Once BinktermPHP ships that entry point, worker mode can be enabled by uncommenting the `worker` block in `config/Caddyfile`.

#### Sysop migration from standalone Caddy

1. Install FrankenPHP: `curl -fsSL https://frankenphp.dev/install.sh | bash`
2. Copy `config/Caddyfile.example` to `config/Caddyfile` and adjust the domain and `root` path.
3. In `config/aio.json`, set `"enabled": true` on the `frankenphp` service.
4. Remove the `"caddy"` entry from `health_checks` (FrankenPHP is now the web server).
5. Stop your existing Caddy/Nginx/PHP server. Run `binktermphp-pm` — FrankenPHP starts automatically.

#### Phase 3 — Full embedding (future)

FrankenPHP's Go embed mode can bake all PHP source files, Twig templates, and static assets into a single self-contained binary at build time, leaving only `config/` and `data/` as external directories. This is tracked separately and deferred until Phase 2 is stable in production.
