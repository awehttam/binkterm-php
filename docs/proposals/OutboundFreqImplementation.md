# Outbound FREQ Web Interface

> **Draft proposal generated by AI; it may not have been reviewed for accuracy.**
> **Created:** 2026-03-15 11:38 PDT
> **Revised:** 2026-08-12 — corrected to reflect the outbound FREQ backend that already exists (see Background); scope narrowed to a web UI/API on top of it; added scheduled background retry via `binkp_scheduler` (`FREQ_POLL_INTERVAL`).

## Summary

BinktermPHP already has a working outbound FREQ (file request) backend: `scripts/freq_getfile.php` lets a sysop request a file from a remote FTN node, either via a classic `.req` file (Bark/WaZOO style, the conventional and most broadly supported approach) or via live-session binkp `M_GET` (FSP-1011), and automatically routes the fulfilled file into the requesting user's private file area on a later session. It is CLI-only today.

This proposal covers exposing that existing backend to any logged-in web user: a "File Requests" page under the Files menu where a user can submit a request against a remote node, choose `.req` or `M_GET` as the delivery mechanism (defaulting to `.req`, since it is unknown in advance whether a given remote supports live-session `M_GET`), and track its status until the file arrives in their inbox/private file area.

## Background

The existing FREQ review (`docs/proposals/FileReqReview.md`) covers the **inbound** side — serving files to remote nodes that FREQ us (`M_GET` handling in `BinkpSession`, `freq_outbound`, `FreqResolver`) — and the netmail-based FREQ path. It is a different concern from this document.

The **outbound** (requesting) side already exists as a CLI tool and supporting classes:

- `scripts/freq_getfile.php` — accepts a node address and one or more filenames/magic names. Default mode builds a `.req` file (FTS-0008 format: optional `!password` line, one filename per line) and queues it via `BinkpClient::addExtraFile()` so it's sent as a normal outbound file transfer for the remote's FREQ processor to pick up. With `-g`, it instead queues live `M_GET` commands via `BinkpClient::addFreqRequest()`, sent during the session by `BinkpSession::sendFreqRequests()` (already wired into `BinkpSession::processSession()` for the originator role).
- `src/Freq/FreqRequestTracker.php` — persists each request as a row in `freq_requests_outbound` (migration `database/migrations/v1.11.0.24_freq_requests_outbound.sql`) with `node_address`, `requested_files` (JSON array), `user_id`, `mode` (`'req'` or `'mget'`), `status` (`'pending'` / `'complete'`), `created_at`, `completed_at`.
- `src/Freq/FreqResponseRouter.php` — called after any session that receives files. It matches received filenames (case-insensitive) against pending requests for that remote node, and for each match calls `FileAreaManager::storeFreqIncoming($userId, $fullPath, $remoteAddress)` to move the file into the requesting user's private file area, then marks the tracker row complete. Files that don't match a pending request (netmail attachments, `.pkt`/`.tic`/infrastructure files) are left alone; `FreqResponseRouter::isInfrastructureFile()` is available to help distinguish these.
- Hostname resolution for nodes that aren't a configured uplink already exists in `BinkpClient::resolveNodeHostname()`: nodelist crash-route info (`NodelistManager::getCrashRouteInfo()`) → uplink lookup (`BinkpConfig::getUplinkForDestination()`) → binkp-zone DNS fallback (`CrashmailService::resolveDestination()`). `BinkpClient::connect()` already falls through this chain and uses an anonymous (empty) password when connecting to a non-uplink node.

None of this is reachable from the web today. There is also a separate, older, **admin-only** FREQ UI: an "ALLFILES" modal in `templates/nodelist/view.twig`, gated by `ENABLE_FREQ_EXPERIMENTAL`, which sends a **netmail** FREQ (`POST /api/messages/send` with `is_freq: true`) rather than a `.req`/`M_GET` request. That modal is out of scope here and is not replaced by this work — it uses a different delivery mechanism (netmail-embedded FREQ) reviewed separately in `FileReqReview.md`.

The use case driving this proposal: a user sees a node in the nodelist that advertises files via magic names (e.g. `NZINTFAQ` at `3:770/220@fidonet`). Today only a sysop with shell access can request it via `freq_getfile.php`. They should instead be able to request it from the web UI, using whichever mechanism (`.req` or `M_GET`) is likely to work for that node, and receive it in their private file area once fulfilled.

## Scope

### In scope
- Feature flag `FREQ_ENABLE_REQUESTS_WEB`, default **true**, gating the nav entry and the API
- Admin daemon command to trigger a FREQ attempt (initial or retry) in the background so a web request isn't held open for the duration of a binkp session
- API endpoint to queue a request (mode-aware: `.req` or `M_GET`) and to list/poll request status
- "File Requests" entry under the Files menu, available to **any logged-in user** (not admin-gated)
- New page/dialog: submit a request (node address, filename/magic name, optional password, mode selector defaulting to `.req`), and list the current user's past/pending requests with status
- **Periodic background retry** of pending requests, driven out of `binkp_scheduler.php`, on an interval configurable via `FREQ_POLL_INTERVAL` (seconds, `.env`) — so a request that fails or isn't fulfilled on the first attempt is retried automatically rather than sitting `pending` forever
- Reusing the existing `freq_requests_outbound` table and `FreqRequestTracker`/`FreqResponseRouter` classes, with additive columns for retry bookkeeping (see Data Model)

### Out of scope (deferred)
- Replacing or merging with the existing admin-only netmail ALLFILES modal (`templates/nodelist/view.twig`, `ENABLE_FREQ_EXPERIMENTAL`) — different mechanism, left as-is
- `freq_status`/`freq_outbound` lifecycle improvements for the inbound-serving path (covered separately in `FileReqReview.md`)
- Denial/failure tracking (`FreqRequestTracker` currently only models `pending`/`complete`; there is no equivalent of "remote sent M_SKIP" or "session failed" status today — see Open Questions)
- Automated tests for the new paths

## Work Items

### 1. Feature flag

Add `FREQ_ENABLE_REQUESTS_WEB` following the existing `ENABLE_FREQ_EXPERIMENTAL` pattern:
- `Config::env('FREQ_ENABLE_REQUESTS_WEB', 'true') === 'true'` as the check, default true
- Exposed as a Twig global (see `src/Template.php:237` for the analogous `freq_experimental_enabled` global) so `templates/base.twig` and `templates/shells/web/base.twig` can gate the nav entry
- Checked server-side in the new API route(s) as well, not just the UI

### 2. Admin daemon command — spawn a FREQ attempt

**File:** `src/Admin/AdminDaemonServer.php`

Add a command (e.g. `freq_request`) modeled directly on the existing `binkp_poll` command (`src/Admin/AdminDaemonServer.php:323-338`), which already demonstrates the pattern of spawning a long-running binkp operation in the background so the calling web request returns immediately:

- Accept `node`, `filenames` (array), `mode` (`'req'`/`'mget'`), `password` (optional), `user_id`
- Spawn `scripts/freq_getfile.php` via `spawnCommand()` with the appropriate flags (`-g` for `mget`), `--user=`, `--password=` as needed
- `freq_getfile.php`'s `resolveUser()` currently defaults to "first active admin" when `--user` is omitted — the daemon command must always pass `--user=` explicitly with the requesting user's username so files are routed to the correct person
- Respond immediately with an acknowledgement; the actual request row is recorded by `freq_getfile.php` itself via `FreqRequestTracker::recordRequest()` before it connects, so the API layer can look up the row afterward rather than needing the daemon to return an ID synchronously (see Open Questions)
- This same command doubles as the retry entry point used by the scheduler (item 3 below): given an existing `freq_requests_outbound` row that's still `pending`, it should re-run the attempt without inserting a duplicate tracker row — `freq_getfile.php` needs a `--request-id=` option so it can attach to an existing row instead of always calling `recordRequest()`

### 3. `binkp_scheduler` — periodic retry of pending requests

**Files:** `src/Binkp/Connection/Scheduler.php`, `scripts/binkp_scheduler.php`

Pending FREQ requests (`freq_requests_outbound.status = 'pending'`) need to be retried automatically — a single failed or unfulfilled attempt shouldn't leave a request stuck forever. Follow the existing `runScheduledCrashmailPoll()` pattern (`src/Binkp/Connection/Scheduler.php:547-584`), which already shows the shape: check an elapsed-time gate, query for pending work, trigger it via `AdminDaemonClient`, update a last-run timestamp. Differences from the crashmail case:

- **Configurable interval, not a hardcoded constant.** `CRASHMAIL_POLL_INTERVAL` is a fixed `300`-second class constant; the FREQ retry interval must instead read `Config::env('FREQ_POLL_INTERVAL', 300)` (seconds) so sysops can tune it, mirroring how `poll_schedule` / `--interval` are already configurable elsewhere in this file. Re-read it each pass (or at least don't cache it only at construction) so a `.env` change takes effect without restarting the daemon, consistent with `refreshConfig()` reloading `BinkpConfig` every loop iteration.
- **Per-node retry, not a single queue-wide flag.** Crashmail has one global "is there pending work" check; FREQ retries need to group pending `freq_requests_outbound` rows by `node_address` (same shape as `FreqRequestTracker::findPendingForNode()`) and gate each node independently, since one slow/unreachable node's retries shouldn't block or throttle retries to a different node. A per-node "last attempted at" is needed for this (see Data Model).
- Add `runScheduledFreqRetries(): void`, called from `runDaemon()` alongside `runScheduledCrashmailPoll()` and `runScheduledHubNodePush()` (`src/Binkp/Connection/Scheduler.php:530-531`)
- For each node with retry-eligible pending rows, call the admin daemon's `freq_request` command in retry mode (item 2) for that node/row rather than reconnecting inline in the scheduler process — keeps the daemon as the single place that spawns binkp sessions, matching every other Scheduler method
- Respect an attempts cap (see Data Model / Open Questions) so a permanently-unreachable node doesn't retry forever

### 4. API endpoints

**Routes:** `routes/api-routes.php`, following the conventions already used by `POST /messages/send` and `POST /binkp/poll` (auth check → validate/parse JSON body → call service → `apiError()`/JSON success response).

- `POST /api/freq/requests`
  - Auth: any logged-in user (`RouteHelper::requireAuth()`), gated by `FREQ_ENABLE_REQUESTS_WEB`
  - Payload: `{ "node": "3:770/220@fidonet", "filename": "NZINTFAQ", "mode": "req", "password": null }` (`mode` one of `"req"` (default) / `"mget"`)
  - Validates `node` (strip `@domain`, `zone:net/node` format) and `filename`
  - Calls the new admin daemon command to spawn the request
  - Returns an acknowledgement; the UI should follow up with a list/poll call to pick up the resulting `freq_requests_outbound` row (there is a small race between spawning and the row being written — poll or retry client-side)
- `GET /api/freq/requests`
  - Returns the current user's own rows from `freq_requests_outbound` (status, mode, node, filenames, timestamps), most recent first
  - Admins may additionally see all users' requests (parity with other admin-visible listings)
- `GET /api/freq/requests/{id}`
  - Single-row status lookup for polling; must verify the row belongs to the requesting user (or requester is admin) before returning it

### 5. UI — "File Requests" page

**Files:** `templates/base.twig`, `templates/shells/web/base.twig` (both must be updated per `templates/CLAUDE.md`), plus a new template for the page itself (e.g. `templates/files/requests.twig`).

- Nav: add a "File Requests" entry under the Files dropdown (see the existing Files menu structure in `templates/base.twig` around the `bbs_feature_enabled('file_areas')` block), visible to any logged-in user, gated by the `FREQ_ENABLE_REQUESTS_WEB` Twig global
- Page: lists the user's requests (node, filename, mode, status, submitted time) with a "New Request" action
- New Request dialog: node address, filename/magic name, optional password, and a mode selector (radio or select) defaulting to **`.req`**, with `M_GET` as the alternative and brief inline guidance that `M_GET` should only be chosen if the remote node is known to support live-session FREQ
- Status polling and AJAX conventions should follow the existing ALLFILES modal in `templates/nodelist/view.twig` (`errorBox`/`window.getApiErrorMessage`/`showSuccess()` helpers, spinner-disable-button pattern) for consistency
- On fulfillment (`status = 'complete'`), tell the user the file is available in their private file area

## Data Model

Reuse `freq_requests_outbound` (migration `v1.11.0.24_freq_requests_outbound.sql`) and `FreqRequestTracker` — no parallel table. The scheduler retry loop (item 3) does need bookkeeping the table doesn't have today, so a small additive migration is in scope:

- `last_attempt_at TIMESTAMPTZ` — set on every attempt (initial send and each retry); this is what `runScheduledFreqRetries()` gates `FREQ_POLL_INTERVAL` against per node, analogous to `hub_nodes.last_push_at` (`src/Binkp/Connection/Scheduler.php:613`)
- `attempts INTEGER NOT NULL DEFAULT 0` — incremented per attempt; gives the retry loop a cap to stop against (mirrors `HUB_OUTBOUND_MAX_ATTEMPTS` / `hub_node_outbound.attempts` in the same file), and lets the UI show "N attempts" instead of a bare "pending"

`FreqRequestTracker` needs corresponding additions: a method to find pending rows grouped/filtered by retry-eligibility (`last_attempt_at` older than the interval, `attempts` under the cap) alongside the existing `findPendingForNode()`, and `recordRequest()`/a new `recordAttempt()` to bump `last_attempt_at`/`attempts` without re-inserting a row when `freq_getfile.php` is invoked with `--request-id=`.

If the web flow needs anything further the CLI path doesn't track (e.g. distinguishing "spawned but not yet connected" from "session in progress" for UI purposes), scope that separately once the UI's polling needs are clearer — don't pre-build it here.

## Open Questions

1. **Getting the request ID back to the UI immediately.** Because the actual `freq_requests_outbound` row is written by the spawned `freq_getfile.php` process (via `FreqRequestTracker::recordRequest()`) rather than by the API request itself, `POST /api/freq/requests` can't synchronously return the new row's ID. Options: (a) have the API insert the tracker row itself (via `FreqRequestTracker` directly, reusing the same class) before spawning the daemon command, passing a `--request-id=` override into `freq_getfile.php` so it doesn't insert a duplicate row; or (b) have the UI poll `GET /api/freq/requests` shortly after submitting and match on node/filename/timestamp. (a) is cleaner and avoids a race — recommended.

2. **Failure/denial visibility.** `FreqRequestTracker` only models `pending`/`complete`. With scheduled retries (item 3) a failed or unfulfilled attempt no longer strands the row forever — it will simply be retried on the next `FREQ_POLL_INTERVAL` tick, up to the `attempts` cap. But there is still no `failed`/`denied` terminal state: once the cap is hit, the row is just pending-forever-but-no-longer-retried, which the UI needs to distinguish from "still actively retrying" (e.g. compare `attempts` against the cap client-side, or add an explicit `exhausted` status — the latter is cleaner and left as a small follow-up rather than bundled into this pass). Remote-side denial (`M_SKIP`) still isn't tracked at all; `BinkpSession::handleSkipCommand()` remains a log-only no-op, so a node that actively refuses a file looks identical to one that's merely unreachable. Hooking `handleSkipCommand()` up to mark the tracker row explicitly denied (rather than waiting out the attempts cap) is a good candidate for the same follow-up.

3. **Multiple requests to the same node.** Already handled naturally: `FreqRequestTracker::findPendingForNode()` returns all pending rows for a node, and `FreqResponseRouter` matches multiple filenames from multiple users' requests in one pass over `files_received`.

4. **Rate limiting / abuse.** Since any logged-in user can now trigger an outbound binkp session to an arbitrary FTN address, consider whether basic rate limiting (e.g. per-user request count per hour) is warranted before opening this to all users — not addressed in this proposal but worth a decision before implementation.

## Implementation Order

1. Migration: `last_attempt_at` / `attempts` columns on `freq_requests_outbound`, plus the corresponding `FreqRequestTracker` methods
2. Feature flag (`FREQ_ENABLE_REQUESTS_WEB`) + Twig global; `FREQ_POLL_INTERVAL` read by the scheduler
3. Admin daemon command (`freq_request`), supporting both initial send and `--request-id=` retry, resolving Open Question 1 (recommend inserting the tracker row from the API layer, not the spawned script)
4. `binkp_scheduler` retry loop (`runScheduledFreqRetries()`)
5. API endpoints (`POST /api/freq/requests`, `GET /api/freq/requests`, `GET /api/freq/requests/{id}`)
6. UI: nav entry + "File Requests" page + New Request dialog
