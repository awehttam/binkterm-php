# Outbound FREQ Web Interface

> **Draft proposal generated by AI; it may not have been reviewed for accuracy.**
> **Created:** 2026-03-15 11:38 PDT
> **Revised:** 2026-08-12 — corrected to reflect the outbound FREQ backend that already exists (see Background); scope narrowed to a web UI/API on top of it; added scheduled background retry via `binkp_scheduler` (`FREQ_POLL_INTERVAL`); new-migration timestamp ID convention applied; resolved open questions on request-ID handoff, attempts-cap → `failed` status, and a per-user concurrency cap (`FREQ_MAX_CONCURRENT_PER_USER`).

## Summary

BinktermPHP already has a working outbound FREQ (file request) backend: `scripts/freq_getfile.php` lets a sysop request a file from a remote FTN node, either via a classic `.req` file (Bark/WaZOO style, the conventional and most broadly supported approach) or via live-session binkp `M_GET` (FSP-1011), and automatically routes the fulfilled file into the requesting user's private file area on a later session. It is CLI-only today.

This proposal covers exposing that existing backend to any logged-in web user: a "File Requests" page under the Files menu where a user can submit a request against a remote node, choose `.req` or `M_GET` as the delivery mechanism (defaulting to `.req`, since it is unknown in advance whether a given remote supports live-session `M_GET`), and track its status until the file arrives in their inbox/private file area.

## Background

The existing FREQ review (`docs/proposals/FileReqReview.md`) covers the **inbound** side — serving files to remote nodes that FREQ us (`M_GET` handling in `BinkpSession`, `freq_outbound`, `FreqResolver`) — and the netmail-based FREQ path. It is a different concern from this document.

The **outbound** (requesting) side already exists as a CLI tool and supporting classes:

- `scripts/freq_getfile.php` — accepts a node address and one or more filenames/magic names. Default mode builds a `.req` file (FTS-0008 format: optional `!password` line, one filename per line) and queues it via `BinkpClient::addExtraFile()` so it's sent as a normal outbound file transfer for the remote's FREQ processor to pick up. With `-g`, it instead queues live `M_GET` commands via `BinkpClient::addFreqRequest()`, sent during the session by `BinkpSession::sendFreqRequests()` (already wired into `BinkpSession::processSession()` for the originator role).
- `src/Freq/FreqRequestTracker.php` — persists each request as a row in `freq_requests_outbound` (migration `database/migrations/v1.11.0.24_freq_requests_outbound.sql`) with `node_address`, `requested_files` (JSON array), `user_id`, `mode` (`'req'` or `'mget'`), `status` (`'pending'` / `'complete'`), `created_at`, `completed_at`.
- `src/Freq/FreqResponseRouter.php` — called after any session that receives files. It matches received filenames (case-insensitive) against pending requests for that remote node, and for each match calls `FileAreaManager::storeFreqIncoming($userId, $fullPath, $remoteAddress)` to move the file into the requesting user's private file area, then marks the tracker row complete. Files that don't match a pending request (netmail attachments, `.pkt`/`.tic`/infrastructure files) are left alone; `FreqResponseRouter::isInfrastructureFile()` is available to help distinguish these.
- Hostname resolution for nodes that aren't a configured uplink already exists in `BinkpClient::resolveNodeHostname()`: nodelist crash-route info (`NodelistManager::getCrashRouteInfo()`) → uplink lookup (`BinkpConfig::getUplinkForDestination()`) → binkp-zone DNS fallback (`CrashmailService::resolveDestination()`). `BinkpClient::connect()` already falls through this chain and uses an anonymous (empty) password when connecting to a non-uplink node.

None of this is reachable from the web today. There is also a separate, older, **admin-only** FREQ UI: an "ALLFILES" modal in `templates/nodelist/view.twig`, gated by `ENABLE_FREQ_EXPERIMENTAL`, which sends a **netmail** FREQ (`POST /api/messages/send` with `is_freq: true`) rather than a `.req`/`M_GET` request. That modal is out of scope here and is not replaced by this work — it uses a different delivery mechanism (netmail-embedded FREQ) reviewed separately in `FileReqReview.md`.

The use case driving this proposal: a user sees a node in the nodelist that advertises files via magic names (e.g. `NZINTFAQ` at `3:770/220@fidonet`). Today only a sysop with shell access can request it via `freq_getfile.php`. They should instead be able to request it from the web UI, using whichever mechanism (`.req` or `M_GET`) is likely to work for that node, and receive it in their private file area once fulfilled.

## Scope

### In scope
- Feature flag `FREQ_ENABLE_REQUESTS_WEB`, default **true**, gating the nav entry and the API
- Admin daemon command to trigger a FREQ attempt (initial or retry) in the background so a web request isn't held open for the duration of a binkp session
- API endpoint to queue a request (mode-aware: `.req` or `M_GET`) and to list/poll request status
- "File Requests" entry under the Files menu, available to **any logged-in user** (not admin-gated)
- New page/dialog: submit a request (node address, filename/magic name, optional password, mode selector defaulting to `.req`), and list the current user's past/pending requests with status
- **Periodic background retry** of pending requests, driven out of `binkp_scheduler.php`, on an interval configurable via `FREQ_POLL_INTERVAL` (seconds, `.env`) — so a request that fails or isn't fulfilled on the first attempt is retried automatically rather than sitting `pending` forever
- **Per-user concurrent request cap**: a user may have at most `FREQ_MAX_CONCURRENT_PER_USER` (default **2**, `.env`-configurable) requests in flight (not yet `complete`/`failed`) at once; `POST /api/freq/requests` rejects new submissions past the cap
- Reusing the existing `freq_requests_outbound` table and `FreqRequestTracker`/`FreqResponseRouter` classes, with additive columns for retry bookkeeping and a `failed` terminal status (see Data Model)

### Out of scope (deferred)
- Replacing or merging with the existing admin-only netmail ALLFILES modal (`templates/nodelist/view.twig`, `ENABLE_FREQ_EXPERIMENTAL`) — different mechanism, left as-is
- `freq_status`/`freq_outbound` lifecycle improvements for the inbound-serving path (covered separately in `FileReqReview.md`)
- Remote-side denial tracking (`M_SKIP`) — `BinkpSession::handleSkipCommand()` remains a log-only no-op; a node that actively refuses a file still looks identical to one that's merely unreachable until it exhausts its attempts and falls to `failed` (see Data Model)
- Automated tests for the new paths

## Work Items

### 1. Feature flag and config

Add `FREQ_ENABLE_REQUESTS_WEB` following the existing `ENABLE_FREQ_EXPERIMENTAL` pattern:
- `Config::env('FREQ_ENABLE_REQUESTS_WEB', 'true') === 'true'` as the check, default true
- Exposed as a Twig global (see `src/Template.php:237` for the analogous `freq_experimental_enabled` global) so `templates/base.twig` and `templates/shells/web/base.twig` can gate the nav entry
- Checked server-side in the new API route(s) as well, not just the UI

Also add:
- `FREQ_MAX_CONCURRENT_PER_USER`, read via `Config::env('FREQ_MAX_CONCURRENT_PER_USER', 2)`, used by the API layer (item 4) to cap in-flight requests per user
- `FREQ_MAX_ATTEMPTS`, read via `Config::env('FREQ_MAX_ATTEMPTS', 5)` (exact default TBD at implementation time), used by the scheduler retry loop (item 3) as the attempts cap before a row falls to `failed`

### 2. Admin daemon command — spawn a FREQ attempt

**File:** `src/Admin/AdminDaemonServer.php`

Add a command (e.g. `freq_request`) modeled directly on the existing `binkp_poll` command (`src/Admin/AdminDaemonServer.php:323-338`), which already demonstrates the pattern of spawning a long-running binkp operation in the background so the calling web request returns immediately:

- Accept `node`, `filenames` (array), `mode` (`'req'`/`'mget'`), `password` (optional), `user_id`, and **`request_id`** (see below)
- Spawn `scripts/freq_getfile.php` via `spawnCommand()` with the appropriate flags (`-g` for `mget`), `--user=`, `--password=`, and `--request-id=<id>` as needed
- **The tracker row is inserted by the API layer, not the spawned script**: `POST /api/freq/requests` (item 4) calls `FreqRequestTracker::recordRequest()` itself, gets the new row's ID back synchronously, and passes it through the admin daemon command to `freq_getfile.php` as `--request-id=`. `freq_getfile.php` needs a new `--request-id=` option so that when it's set, it attaches to that existing row (bumping `last_attempt_at`/`attempts` — see Data Model) instead of calling `recordRequest()` and creating a duplicate. This resolves the original "how does the UI get an ID back immediately" question cleanly — no race, no polling-to-match-up needed.
- `freq_getfile.php`'s `resolveUser()` currently defaults to "first active admin" when `--user` is omitted — the daemon command must always pass `--user=` explicitly with the requesting user's username so files are routed to the correct person
- This same command doubles as the retry entry point used by the scheduler (item 3 below): given an existing `freq_requests_outbound` row that's still `pending`, it re-runs the attempt via the same `--request-id=` path

### 3. `binkp_scheduler` — periodic retry of pending requests

**Files:** `src/Binkp/Connection/Scheduler.php`, `scripts/binkp_scheduler.php`

Pending FREQ requests (`freq_requests_outbound.status = 'pending'`) need to be retried automatically — a single failed or unfulfilled attempt shouldn't leave a request stuck forever. Follow the existing `runScheduledCrashmailPoll()` pattern (`src/Binkp/Connection/Scheduler.php:547-584`), which already shows the shape: check an elapsed-time gate, query for pending work, trigger it via `AdminDaemonClient`, update a last-run timestamp. Differences from the crashmail case:

- **Configurable interval, not a hardcoded constant.** `CRASHMAIL_POLL_INTERVAL` is a fixed `300`-second class constant; the FREQ retry interval must instead read `Config::env('FREQ_POLL_INTERVAL', 300)` (seconds) so sysops can tune it, mirroring how `poll_schedule` / `--interval` are already configurable elsewhere in this file. Re-read it each pass (or at least don't cache it only at construction) so a `.env` change takes effect without restarting the daemon, consistent with `refreshConfig()` reloading `BinkpConfig` every loop iteration.
- **Per-node retry, not a single queue-wide flag.** Crashmail has one global "is there pending work" check; FREQ retries need to group pending `freq_requests_outbound` rows by `node_address` (same shape as `FreqRequestTracker::findPendingForNode()`) and gate each node independently, since one slow/unreachable node's retries shouldn't block or throttle retries to a different node. A per-node "last attempted at" is needed for this (see Data Model).
- Add `runScheduledFreqRetries(): void`, called from `runDaemon()` alongside `runScheduledCrashmailPoll()` and `runScheduledHubNodePush()` (`src/Binkp/Connection/Scheduler.php:530-531`)
- For each node with retry-eligible pending rows, call the admin daemon's `freq_request` command in retry mode (item 2) for that node/row rather than reconnecting inline in the scheduler process — keeps the daemon as the single place that spawns binkp sessions, matching every other Scheduler method
- Rows whose `attempts` has reached the configured cap are excluded from the retry query and instead transitioned straight to **`status = 'failed'`** by the scheduler pass that notices the cap is hit (a `FreqRequestTracker::markFailed(int $id)` method, alongside the existing `markComplete()`) — so a permanently-unreachable node stops being retried and the row lands in a terminal, user-visible state instead of silently going quiet

### 4. API endpoints

**Routes:** `routes/api-routes.php`, following the conventions already used by `POST /messages/send` and `POST /binkp/poll` (auth check → validate/parse JSON body → call service → `apiError()`/JSON success response).

- `POST /api/freq/requests`
  - Auth: any logged-in user (`RouteHelper::requireAuth()`), gated by `FREQ_ENABLE_REQUESTS_WEB`
  - Payload: `{ "node": "3:770/220@fidonet", "filename": "NZINTFAQ", "mode": "req", "password": null }` (`mode` one of `"req"` (default) / `"mget"`)
  - Validates `node` (strip `@domain`, `zone:net/node` format) and `filename`
  - Counts the current user's rows in `freq_requests_outbound` with `status = 'pending'`; if the count is `>= FREQ_MAX_CONCURRENT_PER_USER`, return 429/422 with a clear error rather than queuing
  - Inserts the tracker row itself via `FreqRequestTracker::recordRequest()`, getting the new row's `id` synchronously
  - Calls the new admin daemon command to spawn the request, passing that `id` as `--request-id=`
  - Returns the new row's `id`/status immediately — no race, no follow-up poll needed just to discover the ID (resolves the earlier open question)
- `GET /api/freq/requests`
  - Returns the current user's own rows from `freq_requests_outbound` (status, mode, node, filenames, timestamps), most recent first
  - Admins may additionally see all users' requests (parity with other admin-visible listings)
- `GET /api/freq/requests/{id}`
  - Single-row status lookup for polling; must verify the row belongs to the requesting user (or requester is admin) before returning it

### 5. UI — "File Requests" page

**Files:** `templates/base.twig`, `templates/shells/web/base.twig` (both must be updated per `templates/CLAUDE.md`), plus a new template for the page itself (e.g. `templates/files/requests.twig`).

- Nav: add a "File Requests" entry under the Files dropdown (see the existing Files menu structure in `templates/base.twig` around the `bbs_feature_enabled('file_areas')` block), visible to any logged-in user, gated by the `FREQ_ENABLE_REQUESTS_WEB` Twig global
- Page: lists the user's requests (node, filename, mode, status, submitted time) with a "New Request" action
- New Request dialog: node address, filename/magic name, optional password, and a mode selector (radio or select) defaulting to **`.req`**, with `M_GET` as the alternative and brief inline guidance that `M_GET` should only be chosen if the remote node is known to support live-session FREQ
- Status polling and AJAX conventions should follow the existing ALLFILES modal in `templates/nodelist/view.twig` (`errorBox`/`window.getApiErrorMessage`/`showSuccess()` helpers, spinner-disable-button pattern) for consistency
- On fulfillment (`status = 'complete'`), tell the user the file is available in their private file area

## Data Model

Reuse `freq_requests_outbound` (migration `v1.11.0.24_freq_requests_outbound.sql` — legacy `vX.Y.Z` ID, from before the migration ID format changed) and `FreqRequestTracker` — no parallel table. The scheduler retry loop (item 3) does need bookkeeping the table doesn't have today, so a small additive migration is in scope. Per the current `/new-migration` convention, new migrations use timestamp IDs (`vYYYYMMDDHHMMSS_<description>.sql`, UTC), not the legacy sequential `vX.Y.Z` scheme — e.g. `v20260812000000_freq_requests_outbound_retry_columns.sql` (generate via `php scripts/migration.php create "freq requests outbound retry columns"` at implementation time so the timestamp reflects when it's actually written):

- `last_attempt_at TIMESTAMPTZ` — set on every attempt (initial send and each retry); this is what `runScheduledFreqRetries()` gates `FREQ_POLL_INTERVAL` against per node, analogous to `hub_nodes.last_push_at` (`src/Binkp/Connection/Scheduler.php:613`)
- `attempts INTEGER NOT NULL DEFAULT 0` — incremented per attempt; gives the retry loop a cap (`FREQ_MAX_ATTEMPTS`) to stop against (mirrors `HUB_OUTBOUND_MAX_ATTEMPTS` / `hub_node_outbound.attempts` in the same file), and lets the UI show "N attempts" instead of a bare "pending"

`status` gains a third value, **`failed`**, alongside the existing `pending`/`complete`: once `attempts` reaches `FREQ_MAX_ATTEMPTS`, the scheduler transitions the row to `failed` instead of continuing to retry it (Work Item 3). This makes `status` a proper terminal-or-not signal for both the UI (a `failed` row is done, distinctly from a `pending` one still being retried) and the per-user concurrency cap (Work Item 4), which only counts `pending` rows as "in flight" — `failed` and `complete` both free up a concurrency slot.

`FreqRequestTracker` needs corresponding additions:
- A method to find pending rows grouped/filtered by retry-eligibility (`last_attempt_at` older than the interval, `attempts` under the cap) alongside the existing `findPendingForNode()`
- A method to find pending rows that have reached the attempts cap (for the scheduler to fail out)
- `recordAttempt(int $id)` to bump `last_attempt_at`/`attempts` on an existing row (used when `freq_getfile.php` is invoked with `--request-id=`), instead of `recordRequest()` inserting a new one
- `markFailed(int $id)`, alongside the existing `markComplete()`
- A method to count a user's current `pending` rows, for the concurrency cap check in `POST /api/freq/requests`

If the web flow needs anything further the CLI path doesn't track (e.g. distinguishing "spawned but not yet connected" from "session in progress" for UI purposes), scope that separately once the UI's polling needs are clearer — don't pre-build it here.

## Design Decisions

These were originally open questions; resolved as follows.

1. **Getting the request ID back to the UI immediately — resolved: the API inserts the row.** `POST /api/freq/requests` calls `FreqRequestTracker::recordRequest()` itself and gets the new row's ID back synchronously, then passes that ID through to the admin daemon command as `--request-id=`, which `freq_getfile.php` forwards to attach to the existing row (`recordAttempt()`) instead of inserting a duplicate. No race, no poll-and-match-up needed. See Work Items 2 and 4.

2. **Failure/denial visibility — resolved: attempts cap falls through to `failed`.** Once a row's `attempts` reaches `FREQ_MAX_ATTEMPTS`, the scheduler transitions it to `status = 'failed'` (`FreqRequestTracker::markFailed()`) instead of continuing to retry — a genuine terminal state the UI can distinguish from `pending` (still retrying) and `complete`. Remote-side denial (`M_SKIP`) still isn't tracked at the protocol level — a node that actively refuses a file still just exhausts its attempts and falls to `failed` the same as an unreachable one, rather than failing immediately with a distinct reason. Hooking `BinkpSession::handleSkipCommand()` up to mark denial explicitly (and fail fast instead of waiting out the attempts cap) remains a follow-up, out of scope for this pass.

3. **Multiple requests to the same node.** Already handled naturally: `FreqRequestTracker::findPendingForNode()` returns all pending rows for a node, and `FreqResponseRouter` matches multiple filenames from multiple users' requests in one pass over `files_received`.

4. **Rate limiting / abuse — resolved: per-user concurrency cap.** A user may have at most `FREQ_MAX_CONCURRENT_PER_USER` (default 2, `.env`-configurable) requests with `status = 'pending'` at once; `POST /api/freq/requests` counts the user's pending rows and rejects new submissions past the cap (Work Item 4). This bounds concurrent outbound sessions per user without a time-window rate limit; a per-hour/per-day submission limit could still be layered on later if abuse turns out to be about submission volume rather than concurrency.

## Implementation Notes (as-built)

Everything in Work Items 1–6 shipped essentially as planned. A few things came up during implementation that weren't anticipated above:

1. **`freq_requests_outbound.file_id`** — an additional column (migration `v20260813052421_freq_requests_outbound_file_id.sql`), storing the `files.id` of the routed response file once a request completes. `FreqRequestTracker::markComplete()` now takes an optional `$fileId`; both `FreqResponseRouter::routeReceivedFiles()` and the magic-name fallback (next item) capture the ID returned by `FileAreaManager::storeFreqIncoming()` and pass it through. The "File Requests" UI uses this to hyperlink a completed request's filename straight to the existing file viewer (`openFileInfoModal()` in `public_html/js/file-preview.js`) instead of making the user go find it in Files themselves. Rows completed before this column existed have `file_id = NULL` and were backfilled once by hand via a one-off DB match on owner/node/timestamp against the `files` table — there is no ongoing backfill mechanism, so this is a non-issue going forward.

2. **Magic-name response routing gap, found and fixed.** `FreqResponseRouter::routeReceivedFiles()` only matches by exact (case-insensitive) filename, but a magic name like `ALLFILES` gets expanded by the remote to something else (e.g. `ALLFILES.TXT`) at fulfillment time — documented as a known limitation in the router's own docblock. In practice this meant every magic-name request landed the file successfully but stayed `status = 'pending'` forever (and would eventually be marked `failed` by the attempts-cap logic despite having already succeeded). Fixed in `scripts/freq_getfile.php`: after the router's exact-match pass, any received file that's still unrouted and isn't FTN infrastructure (`FreqResponseRouter::isInfrastructureFile()`) is now attributed directly to *this invocation's own* request — safe because each `freq_getfile.php` run is for exactly one request — and the row is marked `complete` (with `file_id`, per above).

3. **`DELETE /freq/requests/{id}`** — not in the original scope, added afterward so users can clear out old/unwanted request rows. Owner or admin only; does not touch the routed file itself. See `docs/API.md`.

4. **Two bugs surfaced by testing against a live BinktermPHP peer, fixed outside this feature's own files:**
   - **Symmetric-peer EOB ping-pong** in `BinkpSession`: the "always reply to an incoming M_EOB" policy (needed so real `binkd` peers don't log a successful session as `failed` — see `src/Binkp/CLAUDE.md`) causes two BinktermPHP nodes talking to each other to bounce M_EOB back and forth until the full session timeout, since each side's reply is a fresh incoming EOB for the other to reply to. `freq_getfile.php` against another BinktermPHP node hung for the whole session timeout because of this. Fixed by capping auto-replies at `BinkpSession::MAX_EOB_AUTO_REPLIES` (2) — transparent to real `binkd` interop, since it never needs more than two replies from us. Documented in `src/Binkp/CLAUDE.md`.
   - **`AdminDaemonServer::spawnCommand()` is a deliberate no-op on Windows**, relying on the assumption that the underlying work is already spooled to disk and a scheduled poll will pick it up regardless (true for `binkp_poll`). That assumption doesn't hold for `freq_request` — the spawned `freq_getfile.php` process *is* the entire operation, so on a Windows deployment the daemon would log "spawned" and nothing would ever actually run. Fixed with a dedicated `AdminDaemonServer::spawnFreqRequest()` that spawns for real on Windows via `proc_open()` (file-redirected descriptors, no `proc_close()`), matching the detached-process pattern already used for DOSBox-X. Documented in `docs/AdminDaemon.md` ("Adding a New Command").
