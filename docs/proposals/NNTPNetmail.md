## Overview

The NNTP server currently exposes FTN echoareas as newsgroups. It does not expose
**netmail** — private, point-to-point FTN messages — at all. This proposal adds a single
**virtual netmail newsgroup** per authenticated user: a flat group whose articles are that
user's own netmail, readable in any standard newsreader, with `POST` wired to
`MessageHandler::sendNetmail()` so replies and new messages route out through the BinkP
mailer.

The user-visible result is a group such as `BinktermPHP.netmail` that behaves like a
personal mail folder inside a newsreader — new inbound netmail appears as new articles,
and posting to the group (or replying to an article in it) sends netmail.

---

## Why this is not just "another newsgroup"

Echomail and netmail have different shapes, and the existing `src/Nntp/` code leans hard on
the echomail shape:

| Aspect | Echomail (implemented) | Netmail (this proposal) |
|---|---|---|
| Container | `echoareas` row, shared by all subscribers | No area; scoped by `netmail.user_id` |
| Visibility | `EchoareaSubscriptionManager` per-area subscription | Always visible to the authenticated user (config toggle) |
| Addressing | `From:` synthesized from an FTN address; `To:` decorative (`X-Comment-To`) | Both `from_address` and `to_address` are real routable FTN addresses; `To:` is essential |
| Article numbers | `nntp_article_numbers` keyed `(echoarea_id, …)` | Must be keyed `(user_id, …)` |
| Article build | `NntpArticleBuilder` emits `Newsgroups:`/`X-FTN-AREA:`/`SEEN-BY`/`PATH` | None of those apply; a real `To:` header does |
| Posting | `Newsgroups:` header names one or more target areas | The target is an FTN node address the header cannot express |
| Privacy | Group content is shared; leak risk is low | Every query must be `user_id`-scoped or one account reads another's mail |

Because of this, a netmail group cannot reuse the echomail code paths directly. The
recommended structure is a small strategy layer (below) so both message types share the
transport, command dispatch, `Message-ID` construction, header encoding, and threading
helpers without the echomail assumptions bleeding into netmail.

## Architecture

### Group source strategy

Introduce an interface — working name `NntpGroupSource` — that abstracts "where do a
group's articles come from":

```
src/Nntp/
  NntpGroupSource.php          — interface
  EchomailGroupSource.php      — refactor of today's echoarea-backed logic
  NetmailGroupSource.php       — new: netmail-backed, user-scoped
```

Suggested surface:

```php
interface NntpGroupSource
{
    public function groupName(): string;                       // "BinktermPHP.netmail"
    public function description(): string;
    public function isPostable(): bool;                        // maps to LIST ACTIVE flag y/n
    public function ensureNumbered(): void;                    // lazy article-number allocation
    public function bounds(): array;                           // {low,high,count}
    public function range(int $lo, ?int $hi, ?int $limit): array; // [number => messageRowId]
    public function messageIdToNumber(string $messageId): ?int;
    public function loadMessages(array $ids): array;           // id => row
    public function buildArticle(array $row, int $number, ?array $parentIds = null): array;
    public function overviewLine(array $row, int $number, ?array $parentIds = null): string;
}
```

`NntpSession` holds the currently selected `NntpGroupSource` instead of a raw `echoareas`
row, and its command handlers (`GROUP`, `LISTGROUP`, `ARTICLE`/`HEAD`/`BODY`/`STAT`,
`OVER`/`XOVER`, `HDR`/`XHDR`, `LAST`/`NEXT`, `NEWNEWS`) call through the interface. This is
a refactor of existing behavior with no functional change for echomail, done first as its
own commit.

`NntpNewsgroups` gains a synthetic entry for the netmail group so `resolveGroup()`,
`groupMap()`, and the collision/skip scans keep working. `visibleGroups()` in
`NntpSession` appends the netmail source for every authenticated user (subject to config),
independent of echo subscriptions.

### Article numbering

`NntpArticleNumbers` is `(echoarea_id, …)`. Add a parallel, per-user store with identical
semantics (dense per user, never reused, monotonic watermark, retired numbers return
`423`):

```sql
CREATE TABLE nntp_netmail_article_numbers (
    user_id         INT    NOT NULL REFERENCES users(id),
    article_number  BIGINT NOT NULL,
    netmail_id      INT    NOT NULL REFERENCES netmail(id),
    PRIMARY KEY (user_id, article_number)
);
CREATE UNIQUE INDEX ON nntp_netmail_article_numbers (user_id, netmail_id);

CREATE TABLE nntp_netmail_watermark (
    user_id             INT PRIMARY KEY REFERENCES users(id),
    last_article_number BIGINT NOT NULL DEFAULT 0
);
```

Allocation is lazy, mirroring `NntpArticleNumbers::ensureArea()`: at the top of
`GROUP` / `LISTGROUP` / `OVER` / `ARTICLE`-by-number for the netmail source, assign numbers
in `netmail.id` order to any of the user's not-yet-mapped, not-soft-deleted rows, inside
one transaction serialized by the per-user watermark row lock. The insert paths
(`BinkdProcessor`, `MessageHandler::sendNetmail()`) are left untouched.

Soft-deleted rows (`deleted_by_sender` / `deleted_by_recipient`, depending on which side
this user is on) are excluded from `bounds()` and `range()` exactly the way pruned echomail
is — their numbers are retired, the watermark does not roll back.

A one-time migration seeds `nntp_netmail_article_numbers` and `nntp_netmail_watermark` for
existing rows, per user, `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY id)`, idempotent
(`ON CONFLICT DO NOTHING`).

### Inbox vs. sent

`netmail` holds both received mail (`user_id` = recipient) and mail this user sent
(`user_id` = sender, `is_sent = true`). A single flat NNTP group cannot folder them apart.

**Recommendation:** include both, ordered by `netmail.id`, so the group reads like a
unified conversation view and threading (`reply_to_id`) stays intact across a
send/receive exchange. A `netmail_group_include_sent` config flag (default `true`) lets a
sysop restrict it to inbound only. Sent items are marked with an `X-BinktermPHP-Folder:
sent` header so a newsreader can filter if the user wants.

### Article translation

Add a netmail builder (or a mode on a shared builder) that reuses `NntpMessageId`,
`NntpArticleBuilder::encodeHeader()`, `rfcDate()`, `normalizeBody()`, and a
`reply_to_id`-walking `referencesChain()` against `netmail`, but:

- emits a real `To:` header — `"<to_name>" (<to_address>) <handle@f…n…z…domain>` using the
  same synthesis as `fromHeader()`
- keeps `From:` as the sender's real FTN identity (`from_name` / `from_address`)
- **omits** `Newsgroups:`-as-area semantics beyond the literal group name, `X-FTN-AREA`,
  `X-FTN-SEEN-BY`, `X-FTN-PATH`, `X-FTN-Origin`
- adds `X-FTN-From-Address` and `X-FTN-To-Address` for round-tripping
- carries `X-FTN-MSGID` / `X-FTN-REPLY` from `netmail.message_id` / kludge storage
  (`kludge_lines`, `bottom_kludges` — both present on `netmail`)
- `Content-Type` declares `charset=UTF-8` (bodies are already UTF-8 in the DB)
- quote-style conversion (`src/Nntp/NntpQuoteStyle`, see `docs/proposals/NNTPServer.md` —
  "Quote-style conversion") applies here too, with the quoted author taken from the parent
  netmail's `from_name`

`Message-ID` comes from `netmail.message_id` (present since migration
`v1.4.3_add_netmail_message_id.sql`) or the synthetic content hash for older rows, using
the existing `NntpMessageId` helpers with the netmail group name as the scope token.

### Message-ID resolution

`NntpSession::resolveByMessageId()` does an area-scoped `echomail` lookup. Add a
`user_id`-scoped `netmail` lookup for the netmail source. This must be strictly
user-scoped — resolution, `range()`, `bounds()`, `OVER`, `HDR`, and article fetch all carry
`WHERE user_id = :uid` — so one account can never retrieve another's netmail by guessing or
enumerating an ID.

## Sending

NNTP `POST` targets a group by name; the group name cannot express "route to `227:1/200`".
Two resolution paths, both supported:

1. **Reply** — when the article carries `References:` pointing at an article in the netmail
   group, derive the destination from the parent row: `reply_address` if set, else
   `from_address`, with `to_name` from the parent's `from_name`. Zero user friction; covers
   the common case. This reuses `NntpPost::resolveParent()`-style logic against `netmail`.

2. **New message** — require a parseable recipient. Accept either:
   - a `To:` header whose addr-spec this server can invert — the `(z:n/f.p)` display
     comment, or the `f{node}.n{net}.z{zone}.{domain}` host form that
     `NntpArticleBuilder::fromHeader()` emits — or
   - an explicit `X-FTN-To: 227:1/200` header (with `X-FTN-To-Name` optional; defaults from
     the `To:` display name).

   If neither yields a valid FTN address, reject with `441 Cannot determine netmail
   destination`.

Once resolved, hand off to the shared posting method:

```php
$handler->sendNetmail(
    $this->userId, $toAddress, $toName, $subject, $body,
    null /* fromName: resolved by netmail posting policy */,
    $replyToId, false /* crashmail */, '', null, null, false, 'UTF-8', null
);
```

`sendNetmail()` already owns origin-address selection per destination, charset handling,
local-sysop routing, credit debits, outbound-dir writability checks, and spooling — the
NNTP path adds nothing there.

NNTP-specific validation in the netmail post handler:

- **No cross-posting.** A multi-group `Newsgroups:` that includes the netmail group is
  rejected (`441`). Netmail has no cross-post concept.
- **Rate limiting.** Per-user, same pattern as `NntpPost::rateLimitError()` but counting
  `netmail` rows authored by the user in the window. Separate config keys from the echomail
  post limits.
- **Control messages** (cancel / supersede / newgroup) are accepted and dropped, as in
  `NntpPost`.
- **Attachments / FREQ / crashmail** are out of scope for v1 — `sendNetmail()` supports
  them but there is no natural NNTP surface, and a plain newsreader will not produce them.

`POST` gating is unchanged: `480` if not authenticated, `483` if plaintext-auth is
required and TLS is not active, `440` if the server or netmail sending is disabled.

## Receiving

Largely free. Inbound netmail is already tossed into the `netmail` table with `user_id`
resolved by `BinkdProcessor`. Once `NetmailGroupSource` exposes
`WHERE user_id = <authenticated user>`, new inbound netmail simply appears as new articles;
`NEWNEWS` works off `netmail.date_received` the same way the echomail path does.

## Configuration

New behavior keys in `config/nntp.json` (managed through the admin interface, written via
the admin daemon — never directly by a route), read through `NntpConfig`:

- `expose_netmail_group` (boolean, default `true` when the NNTP server is enabled) —
  whether the per-user netmail group is listed and selectable at all.
- `netmail_group_name` (string, default `netmail`) — the leaf name; the full group name is
  `<hierarchy-prefix>.<netmail_group_name>`, using the same prefix convention as echo
  groups (or a fixed `BinktermPHP.` prefix if that reads better — open question).
- `allow_netmail_send` (boolean, default follows the existing `allow_posting`) — whether
  `POST` into the netmail group is honored. When `false` the group is read-only and its
  `LIST ACTIVE` flag is `n`.
- `netmail_group_include_sent` (boolean, default `true`) — include the user's sent netmail
  as articles.
- `netmail_posts_per_minute` (integer, default `5`) and `netmail_posts_per_hour`
  (integer, default `30`) — per-user send rate limits, independent of the echomail post
  limits.

No new `.env` / transport settings — the netmail group rides the existing listeners.

## Design Decisions

1. **Per-user, not shared.** The netmail group's article set is
   `netmail WHERE user_id = <authenticated user>` and nothing else. Two users connected to
   the same server see entirely different articles under the same group name. This is the
   only model consistent with netmail being private.

2. **One group, unified inbox+sent.** Rather than `netmail.in` / `netmail.out` (or
   per-correspondent groups), a single flat group holds everything, ordered by arrival, so
   a send/receive exchange threads correctly. Sysops can restrict to inbound with
   `netmail_group_include_sent = false`.

3. **Reply-derivation is the primary send path.** Deriving the destination from the parent
   article covers the common case with no user configuration. The parseable-`To:` /
   `X-FTN-To:` path exists for composing fresh netmail but is secondary.

4. **Strict user-scoping is a correctness requirement, not a nicety.** Every query path in
   `NetmailGroupSource` and the netmail `Message-ID` resolver carries `user_id`. This is
   the main risk area and gets dedicated tests.

5. **Numbering mirrors the echomail scheme.** Same lazy allocation, same monotonic
   watermark, same retired-number / `423` behavior — just partitioned by `user_id` instead
   of `echoarea_id`. Soft-deleted netmail drops out of the range like pruned echomail.

6. **No new protocol surface.** No new NNTP commands. The netmail group is discovered via
   `LIST` / `LIST ACTIVE` / `NEWGROUPS` like any other group, and served through the same
   `ARTICLE` / `OVER` / `HDR` / `POST` handlers via the `NntpGroupSource` strategy.

7. **Attachments and crashmail deferred.** v1 is plain-text netmail send/receive only.

## Open Questions

- **Prefix.** Should the group be `BinktermPHP.netmail` (fixed), or use each user's
  primary network prefix (`LovelyBits.netmail`)? A fixed prefix is simpler and unambiguous;
  a network prefix is more consistent with the echo groups but meaningless for netmail,
  which is not network-scoped.
- **Sent-item article identity.** A sent message that later bounces or is re-sent — does it
  keep its article number? (Proposed: yes, numbers are never reused; a re-send is a new
  row with a new number.)
- **Local (BBS-internal) netmail.** Messages routed to the local sysop user never hit the
  outbound queue. They should still appear in the recipient's netmail group; confirm
  `BinkdProcessor` / `sendLocalSysopMessage()` set `user_id` consistently.
- **Multiple FTN identities.** A user with a point address on more than one network — the
  `To:`/`From:` synthesis and the destination parser need to handle each network's domain
  slug. `NntpArticleBuilder::fromHeader()` already takes a domain argument; the inverse
  parser must too.

## Implementation Order

1. Refactor the echoarea-backed logic in `NntpSession` behind `NntpGroupSource` /
   `EchomailGroupSource`. No behavior change; existing tests stay green.
2. Add `nntp_netmail_article_numbers` / `nntp_netmail_watermark` + backfill migration
   (via `/new-migration`).
3. `NetmailGroupSource` read path (numbering, bounds, range, build, overview, Message-ID
   resolution) — all `user_id`-scoped.
4. Wire the netmail group into `NntpNewsgroups` and `NntpSession::visibleGroups()` +
   config keys in `NntpConfig`.
5. Netmail `POST` handler: reply-derivation, `To:`/`X-FTN-To:` parsing, rate limiting,
   hand-off to `sendNetmail()`.
6. Admin UI for the new `config/nntp.json` keys (admin daemon command).
7. Tests: numbering table semantics, user-scoping isolation, `To:`-address round-trip,
   reply-derivation.
8. Docs: update `docs/NNTP.md`, and `docs/proposals/NNTPServer.md` Design Decision 3
   (currently "client-facing echomail only").
