# Native Door Hardening: Environment Isolation and Privilege Separation

> **Status: DRAFT.** This proposal was generated by AI and may not have been reviewed for accuracy. File and line references reflect the code at the time of writing and must be re-verified before implementation.

> **Implementation note.** Fix 1 and Fix 2 are implemented. Where the shipped behavior differs from the original design, the sections below describe what shipped and say so. The main differences: the bridge does not probe whether a door user can read `.env` or `config/binkp.json`; `scripts/setup_door_user.sh` changes no ownership or modes unless given `--apply-permissions`; the `doorprobe` test door was dropped; and Docker enables door users with `NATIVEDOOR_DOOR_USERS`.

## Background

A private security report showed that doors launched by the door bridge inherit the bridge's full process environment, which includes the application's `.env` secrets (database login, SMTP login, admin daemon secret). Doors also run as the same OS user as the bridge, so even with a clean environment a door can read `.env` and other application files directly from disk.

Confirmed locations:

- `scripts/dosbox-bridge/multiplexing-server.js` loads `.env` into `process.env` at start and again on reload (`override: true`).
- `scripts/dosbox-bridge/emulator-adapters.js` builds the native door environment as `{ ...process.env, DOOR_* ... }` and passes it to `pty.spawn` (`NativeAdapter.launch`).
- The DOSBox adapter (`emulator-adapters.js`, and the duplicate in `multiplexing-server.js`) spreads `process.env`; when no `env` option is set, Node inherits the full environment anyway.
- The DOSEMU adapter passes `env: process.env`.

Findings about the Docker image (`Dockerfile`, `docker/supervisord.conf`, `docker/entrypoint.sh`):

- The bridge runs under supervisor as `user=binkterm`, not root. A launch strategy that depends on a root bridge does not apply to the shipped image.
- `entrypoint.sh` applies `chmod -R 775` to `data/`, `config/` and `dosbox-bridge/`. The "other" bits give any additional OS user read access to `config/binkp.json` and everything under `data/`. Door user separation is ineffective until these trees are tightened.
- Secrets reach the container through compose `environment:` or `env_file:`, so they live in the real process environment, not only in a `.env` file.

Two fixes are proposed:

1. **Fix 1 - Environment isolation:** doors receive a controlled environment, never a copy of the bridge's.
2. **Fix 2 - Privilege separation:** doors run as dedicated unprivileged OS users that cannot read the application's files, selectable per door.

## Goals and Constraints

- Close the secret leak. The strict environment is the default from the first release, so the cost is a deliberate, documented compatibility break for doors that relied on inherited variables, softened by `env`, `env_passthrough` and an audit of the bundled doors.
- Fix 2 is opt-in and does nothing until a sysop enables it.
- Fail closed when fix 2 is enabled but misconfigured; never silently fall back to running as the app user.
- One shared implementation behind a single launcher interface, used by every adapter, not per-adapter copies.
- Support the two real deployment shapes: Docker (bridge not root, no systemd) and bare metal (commonly systemd).
- Windows and macOS behavior is unchanged except for fix 1.
- Settings are split by who controls them: the door author declares what the door needs (in its manifest), the sysop decides how it is confined (in `config/nativedoors.json`). See **Configuration Split**.

## Configuration Split

A door's `nativedoor.json` ships with the door, so its author controls it. Anything that weakens confinement or exposes bridge secrets must therefore never be decided by the manifest alone.

| Where | Settings | Controlled by |
|---|---|---|
| `native-doors/doors/<door>/nativedoor.json` | `env` (static literal variables), `env_passthrough` (a request for named bridge variables), `writable_paths` | Door author |
| `config/nativedoors.json` (per-door entry, next to `terminal_size`) | `launch_mode` (`direct`, `sudo` or `socket`), the settings for that mode (`run_as` for sudo, socket name for socket), and approval of the door's `env_passthrough` request | Sysop, via the admin UI and admin daemon |

Rules:

- A manifest can never select its own `launch_mode` or `run_as`.
- If a door has no `launch_mode` in `nativedoors.json`, the global default applies. Once any non-direct mode is enabled, a door with no resolved mode is refused, not run as `direct`.
- Static `env` values from the manifest pass through the secret-name denylist like everything else, so a manifest cannot set `DB_PASSWORD` or similar, even as a literal.
- `env_passthrough` in the manifest is only a request. A variable reaches the door only if the sysop has approved it for that door in `nativedoors.json`, and it is never a name matching the secret patterns.
- The lists of permitted door users and sockets stay outside any web-writable file (sudoers group, root-controlled socket directory).

## Fix 1: Environment Isolation

### Strict allow-list (default from the first release)

Doors receive an environment built from scratch. The bridge's `process.env` is never copied, so there is no strip list to maintain and a secret added to `.env` later cannot leak by omission. There is no inherit-and-strip stage: the strict allow-list ships as the default for every door in the first release.

A door's environment consists of exactly these, and nothing else:

- `PATH`, set explicitly by the bridge, never inherited. The default is `/usr/local/bin:/usr/bin:/bin`. A sysop can override it with `NATIVEDOOR_PATH` in `.env`, read with `Config::env()` like the other global defaults.
- `HOME` (the door home), `USER`, `LOGNAME`.
- `TERM`, `LANG`, `COLUMNS`, `LINES`. `TERM` is `xterm-256color`, which is what native doors receive today (set in `NativeAdapter.launch` and again by node-pty from its `name` option). `LANG` is `C.UTF-8`. Nothing in the bridge, Dockerfile or docs sets `LANG` or `LC_ALL` today, so doors currently get whatever the bridge inherited, usually nothing in Docker. `C.UTF-8` is the one deliberate change, and a system without that locale falls back to the `C` locale. `LC_ALL` is not set: it overrides every other locale variable and nothing needs it. A sysop who needs it can use `env` or approved passthrough.
- `DOOR_*` variables set by the bridge.
- Static `door.env` values from the manifest.
- `env_passthrough` names the sysop has approved for that door.
- Adapter extras, such as `SDL_VIDEODRIVER=dummy` and the PubTerm values described below.

The same environment is built for every launch mode, including `direct`, so behavior does not differ between modes. Under sudo the environment is reset and rebuilt from explicit arguments, and under the launcher the child environment is built from the request alone.

Names matching the secret patterns (`DB_*`, `SMTP_*`, `ADMIN_DAEMON_SECRET`, and any `*_SECRET`, `*_PASS`, `*_PASSWORD`, `*_TOKEN`, `*_KEY`; derive the final list from `.env.example` at implementation time) are refused as `door.env` values and as passthrough names. This is a backstop for the manifest-controlled paths, not the primary defense.

Notes:

- The `${VAR:-default}` substitution in launch commands (`emulator-adapters.js`) runs in the bridge process against its own `process.env`, so it is not affected by what the child receives. It is its own leak path: a manifest containing `-x ${DB_PASS:-}` puts the database password into the door's argv, visible in `ps` and to the door. The substitution must apply the same secret-name denylist as `door.env` and passthrough (or a small allow-list of names), and substitute the default for anything refused.
- Escape hatches for doors that need more: `door.env` for static values, and `env_passthrough` for bridge variables, approved by the sysop per door in `config/nativedoors.json` (see **Configuration Split**). Missing variables are skipped quietly.

### Approving env_passthrough Requests

Approval is a per-door checklist in the admin UI's native door settings, next to `launch_mode`, `run_as` and `terminal_size`.

- The sysop sees the variables the door's manifest requests as checkboxes and approves them individually. Saving writes the approved names to that door's entry in `config/nativedoors.json` through the admin daemon.
- Approvals are stored by name. If a manifest update adds a name to `env_passthrough`, that name stays unapproved until the sysop approves it, so a door update cannot widen its own access. Names removed from the manifest are ignored at launch and can be pruned from the approved list.
- Names matching the secret patterns are shown as refused and cannot be approved.
- Unapproved requests are surfaced in two places:
  - The admin UI shows a badge on the door (for example "requests 2 variables, not approved") listing the names.
  - The bridge logs the unapproved names (names only, never values) once per launch at warn level, noting that they were dropped.
- The door still launches without the unapproved variables.

### Compatibility Risk

Starting strict is a breaking change for any door that relied on an inherited variable (for example `TMPDIR`, a library path variable, or a variable a sysop added to `.env` for a specific door). Mitigations:

- Audit every bundled door manifest and launch script in the same release and declare what each needs (see the PubTerm audit below).
- Document the environment contract and `env_passthrough` in `docs/NativeDoors.md`.
- Write the UPGRADING entry so a sysop can act on it without prior context: what doors now receive, how to see which variables a door was given (debug log of names), and how to request and approve a passthrough.

### PubTerm Audit

PubTerm (`native-doors/doors/pubterm/`) was checked to see what it needs under the strict environment. It is a bash script that runs the system `telnet` client against the BBS.

Read by the door process:

| Variable | Read by | Needed | Under the strict environment |
|---|---|---|---|
| `PUBTERM_HOST` | `pubterm.sh` (default `127.0.0.1`) | Yes | Supplied by the bridge as an adapter extra (see findings) |
| `PUBTERM_PORT` | `pubterm.sh` (default `2323`) | Yes | Supplied by the bridge as an adapter extra |
| `PUBTERM_TELNET_BIN` | `pubterm.sh` (default `telnet`) | Optional | Supplied by the bridge when set in its environment |
| `PATH` | `bash`, `command -v telnet`, and the telnet client | Yes | Always set; must include the directory holding `telnet` (for example `/usr/bin`, `/bin`) |
| `TERM` | telnet client, which sends the terminal type | Yes | In the allow-list |
| `HOME` | telnet client (`.netrc`) | No, because `-K` disables auto-login | In the allow-list anyway |

Not needed by the door: `TELNET_USER` (named in a script comment; `-K` disables it) and `LANG` (the client runs with `-8`; harmless if present).

Read by the bridge itself from its own `process.env`, never by the door, so they need no passthrough: `TELNET_BIND_HOST`, `TELNET_PORT` and `PUBTERM_PORT` (used by `_setupPubtermProxyForwarder` to pick the forwarder's target), and on Windows `PUBTERM_PLINK_BIN`, `PUBTERM_HOST` and `PUBTERM_PORT` (expanded by the bridge in `launch_command_windows`).

Findings:

1. **The common Linux path already works.** When the PROXY forwarder is set up, `proxyEnvOverride` supplies `PUBTERM_HOST` and `PUBTERM_PORT` as explicit extras, so the door needs nothing inherited.
2. **The fallback path breaks silently.** When there is no valid client IP or the forwarder fails to start, `_setupPubtermProxyForwarder` returns `{}` and the door falls back to whatever `PUBTERM_HOST` and `PUBTERM_PORT` it inherited, then to `127.0.0.1:2323`. Under the strict environment a sysop's `.env` values would be ignored without any error. The forwarder itself also falls back to `TELNET_PORT` while the door script does not, so the two paths can already disagree.
3. **Recommended fix:** for the pubterm door, the adapter should always resolve the target host and port once (the logic it already uses for the forwarder) and always return `PUBTERM_HOST` and `PUBTERM_PORT` as extras, forwarded or not. It should also pass `PUBTERM_TELNET_BIN` through when set in the bridge environment. These values are not secrets and the bridge, not the manifest author, decides them, so no sysop passthrough approval is needed. This also removes the old idea of a "door-safe `.env` key list" containing `PUBTERM_*` and `TELNET_*`. These values stay a PubTerm-specific adapter extra, decided in bridge code. There is no general mechanism for a manifest to request bridge variables without sysop approval, because that would let any door author widen their own access. Any other door that needs a bridge variable uses `env_passthrough` with sysop approval.

### SyncDOOM Audit

SyncDOOM (`native-doors/doors/syncdoom/`) is a compiled C binary launched as `syncdoom -f {dropfile}`. Its `lobby.js`, `getwads.js` and `syncdoom_lib.js` are Synchronet scripts that the bridge never runs, so they do not affect the environment contract.

- **Environment:** the binary reads very little. Strings in the ELF show `HOME`, `DOOMWADDIR`, `SBBSNODE` and a few other `SBBS*` names, with only three `getenv` call sites in total, so which names are actually read was not determined. `HOME` is in the allow-list. `DOOMWADDIR` and the `SBBS*` names are Synchronet and Doom conventions that nothing sets under this bridge today, so nothing is lost. The manifest needs no `env` or `env_passthrough`. A sysop who sets `DOOMWADDIR` would need passthrough approval.
- **Fix 2 impact:** the Synchronet lobby passes `-home <per-user dir>` to the binary, but the bridge launch command is only `-f {dropfile}`. Without `-home` the door falls back to its launch directory and aborts on the first save. That directory is writable today but becomes read-only for door users under Fix 2. The fix is a manifest change to `-f {dropfile} -home "{homedir}"` (`{homedir}` is the launch-command placeholder for `DOOR_HOME`; quote it so a path with spaces stays one argument), so saves land in `data/users/<id>/<door>`, the default writable location. No `writable_paths` exception is needed.
- **Event log:** the lobby passes `-eventlog` under `data/syncdoom/`, which the bridge launch does not. Leave it unset or point it under `DOOR_HOME`.
- **Read-only inputs:** `wads/` and `syncdoom.ini` should only be read. Confirm the binary does not write into `wads/` during play.

### BBSLink and linuxdoortest Audit

These two doors ship with BinktermPHP. Both are bash scripts, and neither needs a passthrough or a manifest `env`.

- **linuxdoortest:** uses `clear` and `read -n 1 -s`. It needs `PATH` (to find `clear`) and `TERM`, both in the allow-list.
- **bbslinknative (`bbslink.sh`):**
  - It reads no environment variables. Its settings (`host`, `syscode`, `authcode`, `schemecode`) come from `vars.sh` in the door directory, and it sets `TERM=linux` itself before starting `telnet`.
  - It needs `PATH` to find `curl`, `telnet`, `realpath`, `dirname`, `md5sum`, `awk`, `tr`, `fold`, `head`, `sleep` and `clear`. The fixed `PATH` must therefore include `/usr/local/bin` as well as `/usr/bin` and `/bin`, since a sysop-installed `telnet` or `curl` may live there.
  - `curl` uses plain `http://`, so it honors a lowercase `http_proxy` if one was inherited. A sysop who relies on an egress proxy would lose it under the strict environment. That is the one case where `env_passthrough` of `http_proxy` (and `no_proxy`) is plausible, and it needs sysop approval like any other. It is not a secret-pattern name.
  - The `telnet` client may send `USER` as a telnet environment option. Under a non-direct launch mode that value is the door user's name, not the app user's, which is acceptable.
- **Fix 2 impact:** `vars.sh` holds the sysop's BBSLink `authcode`, and it sits in `doors/`, which is readable by door users. Any other door user could read it. The per-door directory mode (3770, no access for other users) in the trust-boundary section closes this, so `vars.sh` needs no special handling. The door writes nothing to its own directory.

### Fix 1 Implementation Plan

1. Create a shared module, for example `scripts/dosbox-bridge/door-env.js`, exporting `buildDoorEnv(extra, options)`. It builds the environment from the allow-list, merges adapter extras and manifest `door.env`, applies approved `env_passthrough`, and drops any secret-named variable from the manifest-controlled inputs. It never reads `process.env` wholesale.
2. Replace each spawn site with `buildDoorEnv(...)`:
   - native door `pty.spawn` env
   - DOSBox spawn in `emulator-adapters.js`
   - DOSBox spawn in `multiplexing-server.js`
   - DOSEMU spawn (`env: process.env`)
   - Always set `env` explicitly, including the non-Linux and non-headless DOSBox branches that currently leave it unset.
3. Keep `SDL_VIDEODRIVER=dummy` as an explicit extra. Change `_setupPubtermProxyForwarder` so the pubterm door always receives `PUBTERM_HOST`, `PUBTERM_PORT` and (when set) `PUBTERM_TELNET_BIN` as extras, forwarded or not (see **PubTerm Audit**).
4. Add the manifest fields `door.env` and `door.env_passthrough`, and the `config/nativedoors.json` approval list, per **Configuration Split**.
5. Log, at debug level only, the variable **names** (never values) passed to each door.
6. Apply the secret-name denylist to the `${VAR:-default}` launch-command substitution (see the notes above).
7. Load `.env` into the bridge through an allow-list instead of `dotenv.config()`: parse it with `dotenv.parse` and set only the names the bridge uses, on start and on the reload path (`override: true`). The allow-list lives in `door-env.js` next to the secret patterns. It must cover `DB_*`, `DOSDOOR_*`, `DOSBOX_EXECUTABLE`, `DOSEMU_EXECUTABLE`, `DOOR_EMULATOR`, `NATIVEDOOR_*`, `TELNET_BIND_HOST`, `TELNET_PORT`, `PUBTERM_*` and any name a bundled manifest substitutes. This is defense in depth, not a security boundary: the bridge's `.env` file is readable by the bridge's own user, and secrets that compose injects into the real process environment are already present before the bridge starts and are not touched by it. The real protections are Fix 2 and starting the bridge with a clean environment (for example `env -i` in the supervisor program). The daemon re-exec and the `door_data_sync.php` spawn still inherit the full environment; the PHP script reads `.env` itself and needs nothing inherited.
8. Tests: see the Test Plan section.
9. Docs: `docs/NativeDoors.md` (environment contract, `env`, `env_passthrough`), `docs/DOSDoors.md` if affected, and an UPGRADING entry.

## Fix 2: Privilege Separation

### Design Overview

Doors run as dedicated unprivileged OS users. Which user a door runs as is configurable per door. Three launch strategies sit behind one interface so the bridge does not care which is in use.

- **`direct`:** today's behavior. Default. The only strategy on Windows and macOS.
- **`sudo`:** the bridge spawns the door through `sudo -n -u <user>`. For bare-metal installs without systemd.
- **`socket`:** the bridge connects to a small launcher process that already runs as the target door user and asks it to spawn the door. The launcher is hosted by systemd socket activation on bare metal, or by supervisor in Docker.

The strategy is chosen explicitly per door with `launch_mode` (`direct`, `sudo` or `socket`) in `config/nativedoors.json`, with an optional global default (`NATIVEDOOR_LAUNCH_MODE`). It is never auto-detected, because a silent choice is how a misconfiguration ends up running doors as the app user, and it is never read from the door's manifest. Different doors may use different modes on the same system. A door whose mode fails preflight refuses to launch.

Fix 2 applies to native doors only. DOSBox and DOSEMU doors run inside an emulator and see only what is mounted into it, so they are not part of this proposal; they still get the Fix 1 environment isolation.

### Launcher Interface

`NativeAdapter.launch` calls `launcher.spawn(spec)` in place of the direct `pty.spawn` (`emulator-adapters.js`). The spec carries argv, the strict environment, cwd, terminal size, and the resolved `run_as` user. Every strategy returns the same pty-like handle: `onData`, `write`, `resize`, `kill`, `forceKill`, `onExit`.

The carrier-loss path in `multiplexing-server.js` currently calls `process.kill(session.emulatorPid, 'SIGKILL')` directly, and probes liveness with `process.kill(pid, 0)`. Both must go through the handle (`forceKill()` and an `isAlive()` check), because the correct behavior differs per strategy and a signal-0 probe can fail with a permissions error that the current code would report as "already exited".

### Per-Door Users

- Add a per-door `run_as` to `config/nativedoors.json` (not the manifest), next to the existing per-door `terminal_size`, and a global default (`NATIVEDOOR_RUN_AS_USER`).
- If a door's mode is non-direct and it resolves to no user, refuse to launch. Never fall back to the app user.
- The set of permitted door users must live somewhere the web application cannot write, so a compromised admin session cannot choose an arbitrary target:
  - **sudo:** the sudoers rule uses a runas group, for example `appuser ALL=(%doors) NOPASSWD: ALL`, which permits any member of the `doors` group. The bridge reads the same membership list.
  - **socket:** the sockets that exist in the root-controlled socket directory are the allowlist. The admin UI offers whichever sockets are present.
  - The bridge additionally refuses uid 0 and the app user's own uid in every mode.
- Each door user has its own primary group, and the app user is a member of every door group. The bridge can then set the group of the directories it creates (`data/users/<id>/<door>`) and create them with mode 2770. Doors are isolated from each other: they cannot read each other's saves or ptrace each other. Users of the same door share that door's uid.
- Parent directories need traverse-only access for door users (mode 0711 or ACLs).

### Trust Boundary: What Door Users May Write

Anything a door user can write must be treated as untrusted by code that runs as the app user. The app user must never include, execute, or follow symlinks through door-writable paths.

This corrects an easy mistake: making the dropfile directory group-writable lets a door pre-plant a symlink at `drops/NODEn/DOOR.SYS`, and the bridge (running as the app user) then overwrites whatever the link points at.

Rules:

- `native-doors/drops/` is owned by the app user and readable, not writable, by door users. `native-doors/doors/` itself is traverse-only for door users (mode 0711). Each door directory under it is owned by the app user, group-owned by that door's group, with mode 3770 (setgid plus sticky). Other door users have no access, so one door cannot read another's files (for example BBSLink's `vars.sh`). Everything shipped in the directory, including `nativedoor.json`, the executable and launch scripts, stays owned by the app user. The manifest's `launch_command` is executed by the bridge's launcher.
- The only door-writable location by default is `data/users/<id>/<door>` (`DOOR_HOME`, created at `emulator-adapters.js` `homeDir`).
- A door can write to its own directory (`cwd` is the door directory). The sticky bit means a door user can create files and change files it owns, but cannot delete, rename or replace files owned by the app user, so the manifest and executables are protected. New files inherit the door's group through setgid, and the `umask 002` wrapper keeps them removable by the app user. The app user must still never execute, include or follow symlinks through anything in that directory that it did not ship.
- A door that edits a pre-shipped file in place (for example a bundled `.ini` or score file) declares it in `door.writable_paths`. The setup step makes just those files owned by the door's user, so the door can also replace them by rename. This is the only case where the manifest declares anything about writing.
- Use explicit `mode` and ownership on directories the bridge creates, not a process-wide `umask`, which would also loosen logs and other files. The door itself is started with `umask 002` (a `sh -c 'umask 002; exec "$@"'` wrapper) so files it creates remain removable by the app user. Otherwise a subdirectory created by the door with a restrictive mode cannot be emptied during cleanup.
- Lock down more than `.env`. `config/binkp.json` (uplink passwords), the other `config/` files and `data/` should also be unreadable by door users. As shipped, the Docker image does this (770/660, shared `binkterm` group) and `setup_door_user.sh --apply-permissions` can do it where the web server and bridge share a group that owns the files. On bare metal the default run leaves file permissions to the sysop, because installs where the web server reaches these files through world access would be locked out by a blanket `o-rwx`. Neither the bridge nor the script verifies this by default.
- All doors of one uid share that uid's view of the system, so harden what is cheap: home directories at 0700, and the kernel's Yama `ptrace_scope` where available. Per-session uids are out of scope.

### Not Used: node-pty uid and gid

The proposal does not use node-pty's `uid` and `gid` spawn options. In the installed node-pty (1.1.0, `src/unix/pty.cc`), the child calls `setgid(gid)` then `setuid(uid)` and nothing else. It never calls `setgroups()` or `initgroups()`, so a root bridge would start the door with the bridge's supplementary groups still attached. The options also take effect only when both are given. If a root-bridge strategy is ever added, wrap the command instead, for example `setpriv --reuid=<uid> --regid=<gid> --init-groups -- <cmd>`, or use `runuser` or `sudo`. Re-check `pty.cc` if the node-pty version changes.

### Strategy: sudo

For bare-metal installs without systemd, where the bridge runs as a normal user.

- Spawn `sudo -n -u <user> -- env <VAR=val ...> sh -c 'umask 002; exec "$@"' sh <cmd> <args>`. The `DOOR_*` variables are passed as `env` arguments because sudo resets the environment, so they are visible in the process list for the session's lifetime. This is acceptable only because the environment is the strict one from fix 1, which holds no secrets.
- The setup script installs a sudoers fragment, validated with `visudo -c`. It must include `Defaults:<appuser> !use_pty`. Current sudo versions default to `use_pty`, which inserts a second pty between sudo and the door and breaks three things: raw cp437 byte passthrough, resize propagation, and the process-session assumption used for teardown.
- **Teardown:** with `!use_pty`, the door stays in the session led by the sudo process (node-pty makes the spawned process a session leader). SIGHUP via the pty is relayed by sudo, but SIGKILL to sudo cannot be caught and would orphan the door. `forceKill()` therefore runs `sudo -n -u <user> pkill -KILL -s <sudoPid>`. Never use `pkill -u <user>`, which would kill other sessions.
- Windows: ignored with a logged notice.

### Strategy: socket (launcher)

**Launcher.** A small program, for example `scripts/dosbox-bridge/door-launcher.js`, running as a door user with no elevated privileges. It already holds the right uid, so it needs no setuid code. It listens on a unix socket and, per connection:

1. Reads a JSON header: argv, environment, cwd, columns, rows.
2. Spawns the door with node-pty, using exactly the header environment (never its own `process.env`) plus nothing else.
3. Relays door output and input over the connection, with a tagged framing so resize and exit status travel in-band.
4. Kills the door's process group when the connection closes. This is permitted because it is the same uid, and it removes the orphan problem.

An exec restriction the sudo strategy cannot offer: by default the launcher refuses to exec anything outside `native-doors/doors/`.

- The check runs on the resolved real path of the executable, so a symlink that points outside the allowed roots is refused.
- It is configurable. The allowed roots are a launcher setting (for example `NATIVEDOOR_LAUNCHER_EXEC_ROOTS`, a colon-separated list defaulting to the installation's `native-doors/doors/`), set where the launcher is hosted: the systemd unit, the supervisor program, or the launcher's own arguments. It is deliberately not in `config/nativedoors.json`, because that file is web-writable and a compromised admin session must not be able to widen what the launcher will run.
- Shipped doors launch through an interpreter (`/bin/bash bbslink.sh ...`), so the executable is outside the roots. A second setting (for example `NATIVEDOOR_LAUNCHER_INTERPRETERS`, defaulting to `/bin/bash`, `/usr/bin/bash` and `/bin/sh`) lists interpreters the launcher accepts. For those, the first non-option argument (the script) must be inside the allowed roots. Any other executable outside the roots is refused.
- An allowed interpreter can still run arbitrary code if given `-c`, so the interpreter rule refuses options that take inline code (`-c`) and requires a script path. This narrows what a compromised bridge can ask the launcher to run, but it does not make the launcher a sandbox. The door user's file permissions remain the real boundary.
- A refused launch is logged with the reason and fails the session, like any other preflight failure.

**Bridge side.** A socket-backed handle implements the same interface as the other strategies, so `NativeAdapter` changes very little.

**Hosting on bare metal (systemd).** One `.socket` unit and one `.service` unit per door user, generated by the setup script. Use `LISTEN_FDS` with `Accept=no` so the launcher has one code path. Units run as `User=<doorUser>` with a clean environment by default and can add sandboxing: `InaccessiblePaths=`, `ProtectSystem=strict`, `NoNewPrivileges=`, `MemoryMax=`, `TasksMax=`, `RestrictAddressFamilies=`. Stopping the unit kills the whole cgroup as a backstop.

**Hosting in Docker (supervisor).** `docker/entrypoint.sh` already generates supervisor programs for optional daemons. Extend it to create the door users and groups and write one supervisor program per door user (`user=<doorUser>`) into `conf.d/enabled/`. Requirements:

- Start the launcher with a scrubbed environment (for example `env -i PATH=... node ...`). Supervisor children inherit the container environment, including compose-injected secrets, and a door running as the same uid can read the launcher's `/proc/<pid>/environ`.
- The bridge (as `binkterm`) must reach the socket and other door users must not. Place each socket in a per-user directory owned by the door user with the `binkterm` group allowed to traverse (for example `/run/binkterm-doors/<user>/`, mode 0750). Door A cannot then connect to door B's launcher.

**Hosting elsewhere.** Any supervisor that can run the launcher as a given user works (runit, s6, or similar). The launcher can also create its own listening socket when not started with `LISTEN_FDS`.

### Setting Location

Per-door `launch_mode`, its mode settings (`run_as`, socket name) and passthrough approvals live in `config/nativedoors.json`, edited through the admin UI. The web server cannot write config files, so changes go through the admin daemon (`scripts/admin_daemon.php`); add or update admin daemon commands as needed. Door-author declarations stay in the manifest. The permitted-user allowlists above are deliberately not part of this web-writable surface. The global defaults (`NATIVEDOOR_LAUNCH_MODE`, `NATIVEDOOR_RUN_AS_USER` and, for Fix 1, `NATIVEDOOR_PATH`) live in `.env`, read with `Config::env()`. They use a `NATIVEDOOR_` prefix, not `DOOR_`, because `DOOR_*` names are the variables the bridge passes to doors and the bridge's own settings must not be confused with them. The existing `DOSDOOR_*` prefix belongs to the bridge's DOS door settings. Per-door entries in `config/nativedoors.json` override the defaults.

### Preflight and Failure Behavior

At bridge start, and again before each launch, for each door whose resolved mode is non-direct (preflight is per door, since doors may use different modes):

- Verify the target user exists and is permitted (group or socket directory), is not uid 0, and is not the app user's uid.
- **sudo:** run `sudo -n -u <user> true`.
- **socket:** connect to the socket and complete a handshake.
- **Write probe:** confirm the door user can write its `DOOR_HOME`. The original design also probed that the door user could not read `.env` or `config/binkp.json` and failed closed if it could. That check was removed in the implementation: it refused every door on installs whose files are world-readable, and file permissions are now the sysop's responsibility on bare metal. The setup script's `--apply-permissions` mode still runs the negative probes after changing permissions.
- On failure, log a clear error through the bridge's established logger and refuse to launch. Do not fall back to the app user.
- A launch that fails because sudo or the socket changed after startup looks to the user like a door that exits instantly. Detect a fast exit carrying sudo's error text (or a failed handshake) and fail the session with a logged cause.
- Surface the state (enabled, healthy, failing) in the admin UI or bridge status output.

### Sysop Setup Script

Existing door directories, saves, dropfiles and home directories are owned by the app user, and door users cannot write to them until permissions change. The code must not change ownership on its own. The shipped sysop-run script, `scripts/setup_door_user.sh`, takes a mode argument (`sudo`, `systemd` or `supervisor`) and a dry-run option. By default it does only steps 1, 4, 5 and 6 below: it creates the accounts and groups and installs the sudoers rule or launcher units, and it changes no ownership or mode on any application file. Steps 2 and 3 run only with `--apply-permissions`, which the Docker entrypoint passes. A bare-metal sysop arranges file permissions themselves (see the Implementation note and the Open Questions). The script:

1. Creates each door user and its group, and the shared `doors` group; adds the app user to every door group.
2. With `--apply-permissions` only: applies the ownership and mode layout from the trust-boundary section: read-only `drops/`, traverse-only `doors/` with each door directory at mode 3770 owned by the app user and the door's group, group-writable setgid `data/users/<id>/<door>`, and the files named in each manifest's `writable_paths` given to the door's user.
3. With `--apply-permissions` only: restricts `.env`, `config/` and `data/` so door users have no access, and runs the negative probes to confirm.
4. In sudo mode: installs the sudoers fragment (runas group, `NOPASSWD`, `!use_pty`), validated with `visudo -c` before activation.
5. In systemd mode: generates and enables the `.socket` and `.service` units per door user. In supervisor mode (used by Docker): writes one supervisor program per door user.
6. Is idempotent and supports a per-door form, for example `--door syncdoom --user door_syncdoom`.

Script rules from `scripts/CLAUDE.md` apply: shebang, executable bit in git, and an entry in `docs/CLI.md`.

### Docker

- Update the `Dockerfile` and `docker/entrypoint.sh` to create door users and groups, generate the supervisor programs, and set directory permissions.
- Tighten the existing `chmod -R 775` on `data/`, `config/` and `dosbox-bridge/` to remove world access (770 for directories, 660 for files). `www-data` and `binkterm` share a group, so PHP is unaffected, but anything else relying on world access would break and needs a test pass.
- The entrypoint currently re-applies ownership and modes on every start; it must preserve the door-specific ownership above.
- The launcher is opt-in in the container image, as on bare metal. The image ships the support, and a sysop enables the door users by setting `NATIVEDOOR_DOOR_USERS` (door ids, each optionally `id=user`) for the service, then chooses the Socket launch mode for each door (or sets `NATIVEDOOR_LAUNCH_MODE=socket`). The entrypoint runs `setup_door_user.sh supervisor --apply-permissions` on every start. It is not enabled by default because a door that fails preflight is refused, bind-mounted volumes on Docker Desktop often ignore `chown` and mode bits, and existing door saves would need ownership changes. The `data/` and `config/` volumes are named volumes, which keep ownership and modes.
- While the launcher is off, doors in the container still run as `binkterm`, the bridge's own user, and can read `.env` and `/proc/<bridge pid>/environ`. Phase 1 therefore does not fully protect compose-injected secrets in Docker, and the upgrade notes must say so and point sysops at enabling the launcher.

## Test Plan

There is a bundled test door, `native-doors/doors/linuxdoortest` (a bash script that prints "hello world"), which serves as the smoke test for each launch mode. The original design added a sibling `doorprobe` door, disabled by default and admin-only, that emitted one JSON line per check. It was built and then removed, so the checks below are not shipped; they remain a reference for what a manual or future automated test should cover:

- **Identity:** uid, gid, supplementary groups, session id and process group. The groups check catches a launch path that fails to reset supplementary groups; the process group check supports teardown tests.
- **Environment:** the names of received variables (never values), plus a flag per secret pattern matched.
- **Expected denials:** can it read `.env`, `config/binkp.json`, `data/`, or the parent process's `/proc/<ppid>/environ`?
- **Expected allowances:** can it write `DOOR_HOME` and read `DOOR_DROPFILE`? Can it write `drops/` or `doors/` (it must not)?
- **Teardown mode:** an argument makes it ignore SIGHUP and sleep, with a `setsid` grandchild, to test `forceKill()` for every strategy.
- **Terminal:** reports `COLUMNS` and `LINES` after a resize, covering resize propagation and cp437 passthrough.

The same assertions run in `direct` mode (establishing the baseline, where the secrets are readable) and in `sudo` and `socket` modes (where the denials must hold). Unit tests cover the launchers (`tests/js/door-launchers.test.js`) and `buildDoorEnv` (`tests/js/door-env.test.js`). The `buildDoorEnv` tests cover (only allow-listed and bridge-supplied variables present, everything else absent, passthrough honored only when approved, secret-named variables cannot be passed through or set via `door.env`, real process environment untouched, and the PubTerm host and port supplied whether or not the forwarder starts). The launcher tests also cover the preflight failure paths.

## Rollout Phases

1. **Phase 1 - Fix 1, strict allow-list.** Shared env module, `door.env` and `env_passthrough` with sysop approval, secret-name backstop, PubTerm adapter change, audit of all bundled door manifests, tests, docs, UPGRADING note. This ships strict by default for every install, including Docker, so the upgrade notes must call out the behavior change.
2. **Phase 2 - Fix 2 for native doors.** Launcher interface, `sudo` and `socket` strategies, the launcher program, per-door `run_as`, and preflight (user, reachability and write checks).
3. **Phase 3 - Packaging.** `setup_door_user.sh` (sudo, systemd and supervisor modes, with permission changes behind `--apply-permissions`), Docker user and supervisor generation, the 775 to 770 permission tightening in the image.

Phase 1 should ship first because it removes the environment leak for everyone. Phases 2 and 3 may ship together or separately.

## Open Questions

- **Bare-metal permissions.** The setup script no longer hardens file permissions by default, so a bare-metal door run through sudo can read `.env` and `config/` unless the sysop restricts them. A proper design needs a shared group for the web server and the daemons (as the Docker image has), and a way to verify both sides keep access. Until that exists, `INSTALL.md` could document the manual steps.
