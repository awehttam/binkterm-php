## Purpose

Many DOS door games keep player state and high scores in flat data files in the game directory (for example `PLAYER.DAT` in Legend of the Red Dragon). The DOS door runtime (see `docs/DOSDoors.md`) launches these games in DOSBox-X but has no knowledge of their data. This proposal adds a registry of per-game parsers that read those files and return normalized player and score data, which the BBS can display as leaderboards or use for credits and rewards.

## Design Goals

- One small class per game; adding a game must not require touching core code beyond registration.
- Parsers are read-only and never write to game files.
- Parsers return a normalized structure so leaderboard UI and APIs are game-agnostic, while still exposing game-specific fields.
- Parsing is pure: bytes in, arrays out. File discovery, caching, and scheduling live outside the parser so parsers are unit-testable from fixture files.

## Architecture

```text
dosdoor.jsn (parser id)  -->  DoorDataParserRegistry  -->  DoorDataParserInterface implementation
                                      |
                              DoorDataService
                     (resolves data dir, reads file, caches)
                                      |
                       leaderboard API / door exit hook / UI
```

Proposed locations:

| Path | Role |
|------|------|
| `src/DoorData/DoorDataParserInterface.php` | Contract every parser implements |
| `src/DoorData/DoorDataParserRegistry.php` | Maps parser ids to parser classes |
| `src/DoorData/DoorDataService.php` | Resolves paths, reads files, caches results |
| `src/DoorData/BinaryRecordReader.php` | Helper for Pascal and fixed-record binary files |
| `src/DoorData/Parsers/LordParser.php` | Legend of the Red Dragon implementation |
| `tests/Unit/DoorData/` | PHPUnit tests and binary fixtures |

## Interfaces

```php
interface DoorDataParserInterface
{
    /** Stable id referenced from dosdoor.jsn, e.g. "lord". */
    public static function getId(): string;

    /** Human-readable game name. */
    public function getGameName(): string;

    /** Files the parser needs, relative to the door's data directory. */
    public function getRequiredFiles(): array;

    /**
     * Parse player records.
     *
     * @param string $dataDir Absolute path to the game's data directory
     * @return array<int, array> List of normalized player entries
     * @throws DoorDataParseException when files are missing or malformed
     */
    public function parsePlayers(string $dataDir): array;
}
```

Each player entry uses this normalized shape:

| Field | Type | Description |
|-------|------|-------------|
| `handle` | string | In-game name |
| `real_name` | string or null | Real name stored by the game, if any |
| `score` | int | Primary ranking value, defined by the parser |
| `score_label` | string | What `score` represents, e.g. "Experience" |
| `last_played` | string or null | ISO 8601 UTC timestamp when the game provides one |
| `deleted` | bool | True for dead or vacated record slots; the service filters these out |
| `stats` | object | Game-specific named fields (level, gold, kills, and so on) |

`stats` keys are free-form but should be lowercase snake_case so the UI can render them generically.

## Registry

```php
DoorDataParserRegistry::register(LordParser::class);
$parser = DoorDataParserRegistry::get('lord'); // null if unknown
```

Built-in parsers are registered in the registry's constructor. The registry rejects duplicate ids. A door opts in by naming a parser id in its `dosdoor.jsn` manifest:

```json
{
  "type": "dosdoor",
  "data_parser": "lord",
  "data_dir": "."
}
```

`data_dir` is relative to the door's directory under `dosbox-bridge/dos/DOORS/<door_id>/`. `DosBoxDoorManifest` validation and `docs/DOSDoors.md` would need to be updated to document these two keys.

## Data Directory Resolution

`DoorDataService` builds the path from the validated door id (using the existing door-id whitelist in `DosBoxDoorManifest`) and the manifest's `data_dir`, then confirms with `realpath()` that the result is still inside `dosbox-bridge/dos/DOORS/`. Parsers receive only the final absolute directory and must not accept paths from users.

Games with per-node data directories need an extension to `data_dir` (for example a `{node}` placeholder); LORD uses a single shared directory.

## When Parsing Runs

Two triggers are proposed:

1. **On door exit**: the bridge reports session end; the service reparses and caches. LORD rewrites its data when the player logs off, so this gives fresh data.
2. **On demand with mtime caching**: the leaderboard API compares each required file's mtime to the cached result and reparses only when it changed.

Cached results are stored as JSON under `data/` or in the database; choosing between those is an open question below. Web code must not write config files, but writing cache data under `data/` is fine.

## Linking Game Players to BBS Users

Game files carry a handle and sometimes a real name, not a BBS user id. Matching options, in order of reliability:

1. **Per-user game directory or recorded handle**: a table mapping BBS user id, door id, and in-game handle, populated when the door is launched (the DOOR.SYS drop file already supplies the BBS user's name).
2. **Real-name match**: if the game stores the DOOR.SYS real name, match against the BBS real name, which the project treats as unique.
3. **Handle match**: weakest, since handles are not unique across BBS users.

Unmatched entries are still shown on the leaderboard, without a profile link.

## Binary Reading Helper

Most DOS games were written in Turbo Pascal or C and store fixed-size records. `BinaryRecordReader` should provide:

- `pascalString(offset, maxLen)`: reads a length byte then up to `maxLen` characters, truncating at the length byte
- `uint8`, `int16`, `uint16`, `int32`, `uint32` little-endian reads (use `unpack` with `v`, `V`, `C`)
- `records(file, recordSize)`: yields fixed-size chunks and throws if the file size is not a multiple of `recordSize`
- Bounds checking on every read, throwing `DoorDataParseException` rather than reading past the buffer

Strings from DOS games are CP437; the reader converts with `iconv('CP437', 'UTF-8//IGNORE', ...)` (mbstring does not support CP437) before returning.

Pascal reals (6-byte `Real` type) appear in some games. Provide a `pascalReal()` decoder only when a game needs it.

## Reference Implementation: Legend of the Red Dragon

`PLAYER.DAT` observations, derived from a 708-byte sample with three players:

- Fixed-size records of **236 bytes** (0xEC). File size must be a multiple of 236.
- The full record layout comes from `LORDSTRC.PAS`, shipped in the LORD directory (valid for 3.20 to 4.08). Records are unaligned Turbo Pascal: `integer` is 2 bytes, `longint` 4, `string[N]` is N+1. The offset table is in the phpDoc of `src/DoorData/Parsers/LordParser.php`.
- Experience (`exp`, offset 158) is used as the score. A blank handle marks a deleted slot.
- Verified against the real `PLAYER.DAT` in `dosbox-bridge/dos/DOORS/LORD`.
- `time` and `last_alive_time` are in-game day numbers, not dates, so `last_played` is null and `last_day` is exposed in `stats`.

`SCORES.*` and daily news files exist as well; start with `PLAYER.DAT` and add them if the rankings LORD computes itself are preferable to computed ones.

## Adding a Parser for Another Game

1. Create `src/DoorData/Parsers/<Game>Parser.php` implementing `DoorDataParserInterface`.
2. Pick a stable lowercase id in `getId()`.
3. Use `BinaryRecordReader` for all binary access; do not call `fopen` or `unpack` directly in parsers.
4. Register the class in `DoorDataParserRegistry`.
5. Set `data_parser` (and `data_dir` if needed) in the door's `dosdoor.jsn`.
6. Add a fixture file under `tests/Unit/DoorData/fixtures/` (use a small, scrubbed sample with fictitious handles) and a PHPUnit test asserting every field.
7. Document the file layout in a table in the parser's phpDoc.

## Safety Rules

- Open game files read-only. The game may hold them open or be mid-write; read the whole file once into memory and parse the buffer.
- Retry once after a short delay if the size is not a record multiple, then fail with `DoorDataParseException`.
- Cap file size (for example 10 MB) before reading.
- Escape handles and strings on output; they are untrusted player input.
- Log failures through `BinktermPHP\Binkp\Logger` to `dosdoor.log`, never `error_log()`.
- Any credit rewards derived from scores must be applied server-side in PHP following the credit rules in `CLAUDE.md`.
- Gate any premium aspects with `License::isValid()`.

## Testing

- Unit tests parse fixture files and compare against expected normalized arrays.
- Add tests for truncated files, zero-record files, and a record with a length byte larger than its field.
- The registry has tests for duplicate registration and unknown ids.

## Open Questions

- Where to cache parsed results: JSON under `data/` or a database table.
- Whether the leaderboard is a standalone page, a section of the door's launch page, or both.
- Whether to award credits for ranking milestones (would need the `/usercredits-workflow` steps).
- Per-node data directory support for games that need it.
- Admin UI exposure for choosing the parser instead of editing `dosdoor.jsn`.
