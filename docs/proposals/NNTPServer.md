## Overview

NNTP (Network News Transfer Protocol, RFC 3977) is the protocol that powers Usenet newsgroups. It provides a well-understood, widely-implemented interface for reading and posting threaded messages — and it maps surprisingly well onto FTN echomail. Adding an NNTP server to BinktermPHP would let users connect with any standard newsreader (Thunderbird, Forte Agent, slrn, tin, etc.) and read or post to FTN echoareas as if they were Usenet newsgroups.

This document explores the conceptual mapping between FTN echomail and NNTP, the mechanical challenges involved, and what a BinktermPHP-native NNTP interface might look like architecturally.

For the complementary design where BinktermPHP acts as an **upstream NNTP client** rather than a user-facing server, see `docs/proposals/NNTPClientTransport.md`. The two proposals should share helper logic for article parsing/building, `Message-ID` generation, header translation, threading, and charset handling rather than implementing those rules twice.

## Background: Why NNTP?

Usenet and Fidonet grew up in the same era and solved the same problem — store-and-forward discussion networks — independently. Their data models are strikingly similar:

| Concept         | Fidonet / FTN              | Usenet / NNTP               |
|-----------------|----------------------------|-----------------------------|
| Message area    | Echoarea (e.g. `BINKTERM`) | Newsgroup (e.g. `alt.bbs`)  |
| Message         | Echomail message           | Article                     |
| Network address | FTN address (z:n/f.p)      | Email address               |
| Unique ID       | `MSGID` kludge             | `Message-ID` header         |
| Thread link     | `REPLY:` kludge            | `References:` header        |
| Transit node    | Hub / uplink               | NNTP server (peer)          |

NNTP gateways for Fidonet have existed since the early 1990s. Historically, tools like `ifgate` and various `uucp`/`inews` pipelines connected FTN hubs to Usenet feeding points. The goal here is a first-class, BinktermPHP-native gateway that serves echomail directly from the database.

## Protocol Mechanics

### Core NNTP Commands

An NNTP server only needs a subset of commands to be useful for reading:

- `LIST [ACTIVE]` — return a list of available newsgroups with article counts
- `GROUP <newsgroup>` — select a newsgroup; server returns article count and number range
- `ARTICLE <n>` / `HEAD <n>` / `BODY <n>` — retrieve article by number or Message-ID
- `OVER` / `XOVER` — overview data (subject, from, date, message-id, references) for a range
- `NEWNEWS` / `NEWGROUPS` — incremental sync since a given timestamp

For posting, the server additionally needs:

- `POST` — accept a new article from the client
- `AUTHINFO USER` / `AUTHINFO PASS` — authenticate before posting
- `STARTTLS` — upgrade a port-119 plaintext connection to TLS before `AUTHINFO`

This is a modest surface area. The heavy lifting is in the translation layer, not the protocol itself.

### SSL / TLS

Standard NNTP runs on port 119. NNTPS (implicit TLS) runs on port 563. The daemon must support **both**:

- **Port 119** — plaintext, with `STARTTLS` upgrade (RFC 4642) so a client can negotiate TLS mid-session, similar to how the telnet server handles raw connections before handing them upward.
- **Port 563** — implicit TLS. The listener is opened with an `ssl://` transport and `stream_socket_server`, so the handshake completes on `accept` before any NNTP dialogue.

Both listeners run in the same daemon process (two `stream_socket_server` sockets multiplexed in the accept loop). TLS is provided by PHP's OpenSSL stream layer via `stream_socket_enable_crypto()` / an `ssl://` context — no external TLS terminator required.

**Plaintext credential handling on port 119.** By default, `AUTHINFO USER` / `AUTHINFO PASS` and `POST` are rejected with a `483` ("secure connection required") on an unupgraded port-119 connection — the client must issue `STARTTLS` and complete the TLS handshake first. This default can be relaxed with the `allow_plaintext_auth` behavior setting (see Configuration): when enabled, `AUTHINFO` and `POST` are permitted over an unencrypted port-119 connection for compatibility with older newsreaders that do not implement `STARTTLS`, at the cost of exposing BinktermPHP account passwords to cleartext transmission. Port 563 (implicit TLS) is always encrypted and is unaffected by this setting. When `allow_plaintext_auth` is enabled, the daemon should log authentication events that occur over an unencrypted connection distinctly (e.g. "authenticated via unencrypted AUTHINFO"), so sysops running with the setting on retain visibility into plaintext-auth usage.

Certificate handling mirrors `scripts/gemini_daemon.php`. The cert and key paths come from `.env` via `Config::env()`:

```
NNTP_TLS_CERT_PATH   # PEM cert (or combined cert+key PEM); default data/nntp/server.crt
NNTP_TLS_KEY_PATH    # PEM private key; default data/nntp/server.key
```

If `NNTP_TLS_CERT_PATH` is set and the file exists, it is used as-is (an external/CA-issued cert). If it is unset and no cert exists at the default path, the daemon self-signs one on first start — preferring the `openssl` CLI (reliable on Windows + OpenSSL 3.x) and falling back to PHP's `openssl_*` functions. A missing file at an explicitly-configured path is a fatal startup error, not a trigger to self-sign. The `local_cert` may be a combined cert+key PEM.

Bind host and ports are likewise `.env`-driven, consistent with the other daemons:

```
NNTP_BIND_HOST       # default 0.0.0.0
NNTP_PORT            # plaintext + STARTTLS, default 8119
NNTP_TLS_PORT        # implicit TLS, default 8563; empty disables the listener
```

The port defaults are the unprivileged `8119` / `8563` (following the telnet daemon, which defaults to `2323` / `8023`) so the daemon needs no `CAP_NET_BIND_SERVICE` or root. A sysop serving the well-known `119` / `563` redirects them with an `iptables` / `nftables` rule, exactly as documented for the FTP daemon's port 21, or sets `NNTP_PORT` / `NNTP_TLS_PORT` explicitly and grants the bind capability. The rest of this document says "port 119" / "port 563" to mean the plaintext and implicit-TLS listeners regardless of their actual numbers.

For `STARTTLS` on the plaintext listener, the crypto method should be negotiated **after fork** in the child, so the parent's socket close does not emit a `close_notify` alert before the child responds (same ordering caveat as the gemini daemon).

## Mapping FTN Echomail to NNTP

### Newsgroup Name Translation

Synchronet's NNTP server uses the convention `NetworkDisplayName.AreaTag` in mixed case (e.g. `LovelyBits.BinktermPHP`), preserving the original area tag casing rather than lowercasing. NNTP newsgroup names are case-insensitive by spec, so either convention works. BinktermPHP should follow the same pattern: use the network's display name as the hierarchy prefix and the area tag as-is.

```
Network "LovelyBits", area LVLY_BINKTERMPHP  →  LovelyBits.LVLY_BINKTERMPHP
Network "DoveNet",    area DOVE-NET.GENERAL  →  DoveNet.DOVE-NET.GENERAL
```

The original area tag is also preserved verbatim in the `X-FTN-AREA` header (see below).

**Collision handling** — If two networks share an area tag, the network display name prefix differentiates them. The server should detect and log any collision at startup.

### Message-ID Construction

Rather than a generic `@ftn` domain, the Message-ID should use the BBS's own FQDN, following Synchronet's convention. The raw `MSGID` serial and address are preserved in the `X-FTN-MSGID:` header for round-trip fidelity. The constructed `Message-ID` is scoped to this system and used only by NNTP clients.

**Both halves of the FTN `MSGID` must be folded into the constructed `Message-ID`.** An FTN `MSGID` kludge is `<origin-address> <serial>` (e.g. `227:1/200 6A08C568`), and its uniqueness comes from the *pair*. The serial alone is not globally unique — it is commonly `time()` in hex or a per-session counter that resets on tosser restart, so two different nodes emitting the same serial into the same area is entirely plausible. A `Message-ID` construction that keys only on the serial would let two unrelated messages collide. Including the origin address makes the NNTP `Message-ID` exactly as unique as the FTN identity it represents.

Messages without a `MSGID` kludge (which exist in older traffic) need a synthetic ID. It is derived from a hash of the message's **raw wire content as received** — the original kludge/control lines (`kludge_lines`) concatenated with the message body (`message_text`) — **combined with the originating address** (taken from the packet origin / `PATH` when no kludge is present). The hash input is deliberately the raw stored FTN representation, taken before any NNTP header translation: `NNTPArticle`'s translation logic (header naming, `From:` synthesis, `format=flowed` handling, threading) may evolve over time, and a synthetic `Message-ID` must stay stable across those changes. Nothing produced by the translation layer may feed the hash. Scoping the hash to the origin address also means the same body legitimately crossposted from two different nodes does not collide — it narrows the remaining ambiguity to genuine same-origin duplicates, which is a known and acceptable weakness of any FTN/NNTP bridge.

### Header Translation

Synchronet's output is a useful reference for which headers to emit. BinktermPHP should follow the same conventions:

| FTN field / kludge  | NNTP header             | Notes                                                    |
|---------------------|-------------------------|----------------------------------------------------------|
| `From:` (name)      | `From:`                 | `"Name" (z:n/f.p) <user@fN.nN.zN.fidonet>` — see below |
| `Subject:`          | `Subject:`              |                                                          |
| `To:` (name)        | `X-Comment-To:`         | Synchronet convention; `To:` header is omitted           |
| `MSGID:` kludge     | `Message-ID:`           | Origin address + serial both folded in; see format below; raw value also in `X-FTN-MSGID:` |
| `REPLY:` kludge     | `References:`           | Single parent; raw value also in `X-FTN-REPLY:`          |
| `date_written`      | `Date:`                 | May be wrong; see note below                             |
| `date_received`     | `X-Date-Received:`      | Reliable server-side timestamp; see Date reliability     |
| Echoarea tag        | `Newsgroups:`           | Translated name; raw tag in `X-FTN-AREA:`                |
| `PID:` kludge       | `X-FTN-PID:`            |                                                          |
| `CHRS:` kludge      | `X-FTN-CHRS:`           | Raw wire value; `Content-Type` always declares `UTF-8`   |
| `SEEN-BY:` lines    | `X-FTN-SEEN-BY:`        |                                                          |
| `PATH:` kludge      | `X-FTN-PATH:`           |                                                          |
| BBS hostname        | `Path:`                 | `hostname!not-for-mail`                                  |
| —                   | `Content-Type:`         | `text/plain; charset=UTF-8; format=flowed`               |

#### From address

Synchronet encodes the FTN address into a structured email-like address using the `.fidonet` pseudo-domain:

```
"awehttam" (227:1/200) <awehttam@f200.n1.z227.fidonet>
```

The format is `"DisplayName" (zone:net/node.point) <username@f{node}.n{net}.z{zone}.fidonet>`. Point 0 is included literally. This is non-routable but unambiguous and round-trippable.

#### Message-ID format

Synchronet uses the BBS's own FQDN as the domain rather than a generic `@ftn` placeholder, which produces IDs that are scoped to the originating system. Its observed local part is `MSGID_SERIAL.sequence.AREANAME_LOWERCASED`, e.g. `<6A08C568.55.lovelybitslvly_binktermphp@revpol.lovelybits.org>` — but that form omits the origin address and is collision-prone across nodes.

BinktermPHP folds the origin address in:

```
<{MSGID_SERIAL}.{ORIGIN_ADDR}.{AREANAME_LOWERCASED}@{bbs.hostname}>
```

where `ORIGIN_ADDR` is the `MSGID` address rendered token-safe as `z{zone}n{net}f{node}p{point}` (point `0` included literally), e.g. address `227:1/200` and serial `6A08C568` in area `LVLY_BINKTERMPHP`:

```
<6A08C568.z227n1f200p0.lvly_binktermphp@bbs.hostname>
```

This keeps the ID human-readable and round-trippable while making it as unique as the underlying FTN `MSGID`. For messages with no `MSGID` kludge, the local part is `{content-hash}.{ORIGIN_ADDR}.{AREANAME_LOWERCASED}`, where `content-hash` is a hash (e.g. SHA-256, truncated and base36-encoded) of the raw stored wire content — `kludge_lines` concatenated with `message_text` — and never of any `NNTPArticle`-translated form, so the ID does not shift if the translation logic changes.

BinktermPHP should use `Config::getSiteUrl()` to derive the hostname component.

#### Date reliability

`date_written` from the FTN packet is used for the `Date:` header because that is what newsreaders display and sort by. However, `date_written` can be wrong if the remote sysop's clock is skewed. The reliable `date_received` timestamp should be included as `X-Date-Received:` so discrepancies are visible.

### Article Numbering

NNTP article numbers are per-group integers that increase monotonically and, per RFC 3977, must never be reused within a group. **Decision: article numbers are assigned through a dedicated per-echoarea mapping table, not derived from `echomail.id`.**

Deriving numbers from `echomail.id` does not work. `echomail.id` is a single auto-increment column shared across every echoarea, so messages from other areas interleave between any given area's rows. Applying a fixed offset to `id` therefore does not produce a dense per-group sequence, and if old `echomail` rows are ever pruned, an `id`-derived scheme risks violating the "never reused" requirement.

The mapping table, plus a per-area high-water mark:

```sql
CREATE TABLE nntp_article_numbers (
    echoarea_id     INT NOT NULL REFERENCES echoareas(id),
    article_number  BIGINT NOT NULL,
    echomail_id     INT NOT NULL REFERENCES echomail(id),
    PRIMARY KEY (echoarea_id, article_number)
);
CREATE UNIQUE INDEX ON nntp_article_numbers (echoarea_id, echomail_id);

CREATE TABLE nntp_area_watermark (
    echoarea_id         INT PRIMARY KEY REFERENCES echoareas(id),
    last_article_number BIGINT NOT NULL DEFAULT 0
);
```

**Numbers are allocated lazily by the NNTP daemon, not at echomail-insert time.**
The many code paths that insert an `echomail` row (the inbound tosser, `MessageHandler::postEchomail()`, hub fanout, QWK import) are left untouched; instead the daemon's `NntpArticleNumbers::ensureArea()` runs at the top of `GROUP` / `LISTGROUP` / `OVER` / `ARTICLE`-by-number and assigns numbers to any not-yet-mapped approved rows in the area, in `echomail.id` (arrival) order, inside one transaction:

```sql
-- take the per-area lock (creating the watermark row on first use)
INSERT INTO nntp_area_watermark (echoarea_id, last_article_number)
     VALUES (:echoarea_id, 0)
ON CONFLICT (echoarea_id)
  DO UPDATE SET last_article_number = nntp_area_watermark.last_article_number
  RETURNING last_article_number;   -- :wm

INSERT INTO nntp_article_numbers (echoarea_id, article_number, echomail_id)
SELECT :echoarea_id,
       :wm + ROW_NUMBER() OVER (ORDER BY em.id),
       em.id
FROM echomail em
WHERE em.echoarea_id = :echoarea_id
  AND COALESCE(em.moderation_status, 'approved') = 'approved'
  AND NOT EXISTS (SELECT 1 FROM nntp_article_numbers n
                  WHERE n.echoarea_id = :echoarea_id AND n.echomail_id = em.id)
ORDER BY em.id;

UPDATE nntp_area_watermark
   SET last_article_number = last_article_number + :allocated_count
 WHERE echoarea_id = :echoarea_id;
```

The row lock the watermark `UPDATE` takes serializes concurrent allocations within an area without a separate sequence object per area, and works even for an area with no articles yet (a `MAX(article_number) + 1` scheme does not serialize when there are zero rows to lock). Crucially, the watermark **only ever increases**: once a number is assigned to an `echomail` row it is never reassigned, and if that row — even the highest-numbered one in the area — is later pruned, the watermark does not roll back, so the number is retired rather than reissued. Requests for a retired number return `423`, consistent with the article-expiry design decision below.

The `GROUP` response's reported values derive from these two tables: the high water mark (`HIGH`) is `nntp_area_watermark.last_article_number` — **not** `MAX(article_number)` over the live rows, which would shrink if the top article were pruned — the low water mark (`LOW`) is `MIN(article_number)` over the area's surviving rows (or `HIGH + 1` when the area has none), and the estimated article count is `COUNT(*)` of those rows.

#### Backfill for Existing Data

The current `echomail` table holds roughly 100,000 rows that predate the mapping table, so a one-time migration seeds `nntp_article_numbers` at deploy time, before the new-message numbering path goes live:

- A single set-based `INSERT ... SELECT` using `ROW_NUMBER() OVER (PARTITION BY echoarea_id ORDER BY id)` to assign each area's rows a dense `1..N` sequence.
- Ordered by `id`, not `date_written` — `date_written` can be skewed by a remote system's clock (see the Date reliability note above), whereas `id` reflects true local insertion order.
- After backfill, an area's `LOW` water mark reflects its oldest surviving row, not its true historical first message. This is expected and does not violate the RFC.
- The same migration seeds `nntp_area_watermark` from the result: `last_article_number` for each area is set to that area's highest backfilled `article_number` (`INSERT INTO nntp_area_watermark SELECT echoarea_id, MAX(article_number) FROM nntp_article_numbers GROUP BY echoarea_id`).
- The migration is idempotent — safe to re-run, e.g. skipped entirely if `nntp_article_numbers` is already populated, or written as `INSERT ... ON CONFLICT DO NOTHING` keyed on `(echoarea_id, echomail_id)` with the watermark seed as `ON CONFLICT (echoarea_id) DO NOTHING`.

### Encoding

BinktermPHP stores all message bodies as UTF-8 in PostgreSQL regardless of the original wire encoding, so the NNTP server can serve bodies directly without any conversion. Inbound posts from a newsreader arrive as UTF-8 (NNTP is UTF-8 native) and can be injected into the outbound queue as-is. The `Content-Type` header on served articles should declare `charset=UTF-8`.

## Threading

FTN threading is subject-based by convention — replies share the same `Subject:` and set `REPLY:` to the `MSGID` of the parent. This maps directly to NNTP `References:`. However, FTN only tracks a single parent (`REPLY:`), while NNTP `References:` is a full ancestor chain. The gateway can build a synthetic chain by walking the database for the thread root, but this is an optional enhancement; a single-parent `References:` already enables threaded view in most newsreaders.

## Bidirectional Posting

Read-only access is straightforward. Two-way posting adds complexity:

1. **Authentication** — The NNTP daemon must authenticate the user before accepting a `POST` command. BinktermPHP's existing user accounts and passwords are the natural auth source.
2. **Address assignment** — Posts injected into FTN need a `MSGID` with a valid FTN address. The BBS's own node address is used (the same address used for netmail).
3. **Injection path** — The new message must be written to the outbound packet queue via the **shared echomail posting method** — the same one the web interface uses (`MessageHandler::postEchomail()`) — not by writing raw FTN packets directly. This ensures kludge generation and dupe-check logic are applied consistently. Note that `postEchomail()` itself enforces no cross-posting limit: that check is the caller's responsibility. The web API route (`routes/api-routes.php`) applies `max_cross_post_areas` before calling `postEchomail()`, and the terminal composer posts through that same API route, so both share that one enforcement point. `NNTPPost` runs in the daemon and does not go through that HTTP route, so it needs its own equivalent check (see item 4).
4. **Cross-post limits** — An NNTP client expresses cross-posting as a comma-separated `Newsgroups:` header (e.g. `Newsgroups: LovelyBits.AREA1, LovelyBits.AREA2`). `NNTPPost` must parse this header, resolve each listed group back to its echoarea, and enforce a maximum count before injection. This check is independent of the existing `max_cross_post_areas` enforcement: that logic currently lives in the web API route (`routes/api-routes.php`), not in the shared `MessageHandler::postEchomail()` method, so the NNTP write path — which does not go through that HTTP route — does not inherit it and needs its own equivalent setting (see Configuration). Note also that the API route silently **truncates** an over-limit cross-post list to the first N areas; the NNTP path instead **rejects outright** — with response code `441` ("Posting failed"), consistent with how post-rate-limit rejections are handled elsewhere in this document — since a newsreader that sees its post accepted has no way to learn some target groups were dropped.
5. **Cancel / supersede** — NNTP supports cancel and supersede control messages. FTN has no equivalent. These should be silently dropped at the gateway boundary.
6. **Flood and abuse** — Because the NNTP client is any third-party tool, two limits guard the BBS's FTN node against flooding its uplinks: a per-authenticated-user post rate limit (max posts per minute / hour; rejected with `441`, see Design Decision 2) and a per-source-IP concurrent connection cap (see Connection Limits below).

### Connection Limits

The daemon enforces a maximum number of concurrent connections per source IP address, checked in the parent process's accept loop **before forking** a child for the new connection. This protects the fork-per-connection daemon model from resource exhaustion via many simultaneous connections from a single source, independent of the per-user post rate limits above (which only govern posting frequency after authentication).

- **Default: 3 concurrent connections per IP**, configurable via `max_connections_per_ip` (see Configuration).
- A connection attempt that would exceed the limit is refused at accept time — the parent sends a `400` response line and closes the socket immediately, without forking a child or queueing the connection.
- The limit applies both before and after authentication. It is IP-scoped, not user-scoped, so it is the only throttle available before a client has authenticated.
- The cap is only meaningful in the forking model. In the Windows single-connection fallback (see Architecture) the daemon handles one connection at a time regardless, so the setting has no additional effect there.
- **Out of scope for this design:** per-session command-rate limiting (e.g. capping `LIST` / `ARTICLE` requests per second within an already-open connection). This is deferred as a possible future enhancement, noted here so it is not mistaken for an oversight.

## Architecture

### Daemon Model

Following the pattern of the other protocol daemons in `scripts/` (`gemini_daemon.php`, `ftp_daemon.php`, `mrc_daemon.php`), the NNTP server would be a standalone PHP daemon with a thin entry point and its supporting classes under `src/Nntp/`:

```
scripts/nntp_server.php  — entry point, listens on TCP (default 8119/8563)
src/Nntp/
  NNTPSession.php        — per-connection state machine
  NNTPArticle.php        — echomail → NNTP article translation
  NNTPGroupList.php      — area → newsgroup mapping, LIST support
  NNTPPost.php           — inbound article → echomail injection
```

The entry point follows `scripts/CLAUDE.md` (shebang, `src/functions.php` include, `chmod +x` + `git update-index --chmod=+x`) and is registered in `docs/CLI.md` and the daemon launchers (`restart_daemons.sh`, `start_daemons_windows.*`). Placing the helper classes in `src/Nntp/` keeps them available to the companion `NNTPClientTransport` design without a second implementation.

**Concurrency model — forking, with a Windows fallback.** The daemon uses `pcntl_fork()` to handle each accepted connection in a dedicated child process (the model used by `scripts/gemini_daemon.php`): the parent loop only accepts and forks, the child owns the client socket for the life of the session, and the parent reaps children with `pcntl_waitpid(-1, ..., WNOHANG)` on `SIGCHLD`. Each child opens its own `Database::getInstance()` PDO handle after forking rather than sharing the parent's.

`pcntl` is not available on Windows. When `function_exists('pcntl_fork')` is false the daemon degrades to a **single-connection, blocking** loop: it accepts one client, handles the whole session inline, then returns to `accept`. This is sufficient for local debugging and testing on Windows and is explicitly not intended for production concurrency. All per-connection logic therefore lives in `NNTPSession` and must not assume it is running in a child process.

The daemon reads echomail directly from PostgreSQL via `Database::getInstance()`.

If BinktermPHP also implements the upstream polling/posting design from `docs/proposals/NNTPClientTransport.md`, the server and client sides should reuse shared NNTP helpers rather than maintaining separate implementations of article/header translation behavior.

### Read Path

```
Newsreader → NNTP daemon → PostgreSQL (echomail table)
                        ↑
                  NNTPArticle translates rows to RFC 3977 wire format
```

### Write Path

```
Newsreader → NNTP daemon → NNTPPost validates & authenticates
                        → injects via the shared posting path (MessageHandler::postEchomail) → outbound queue
                        → BinkP mailer picks up on next poll
```

### Configuration

Settings split into two tiers, matching how the other daemons are configured:

**Transport / process — `.env` via `Config::env()`** (needs a daemon restart to take effect, and the web process cannot write these anyway):

- `NNTP_BIND_HOST` (default `0.0.0.0`)
- `NNTP_PORT` (plaintext + `STARTTLS`, default 8119 — redirect 119 to it, or set explicitly)
- `NNTP_TLS_PORT` (implicit TLS, default 8563 — redirect 563 to it, or set explicitly; empty disables the listener)
- `NNTP_TLS_CERT_PATH` / `NNTP_TLS_KEY_PATH` (self-signed automatically if unset; fatal if set but missing)

**Behavior — `config/nntp.json`, managed through the BBS admin interface** (written via the admin daemon, never directly by a route):

- Enable/disable the NNTP server entirely (disabled by default)
- Newsgroup prefix / network-name hierarchy convention
- Allow posting vs. read-only
- Post rate limit: max posts per minute (default 10)
- Post rate limit: max posts per hour (default 60)
- `max_cross_post_areas` (integer, default `5`) — maximum number of echoareas a single NNTP-injected post may target via the `Newsgroups:` header. Matches the existing web/terminal setting of the same name and default, but is configured and enforced independently, since that check lives in the web API route (which the NNTP daemon does not go through) rather than in the shared `postEchomail()` method.
- `max_connections_per_ip` (integer, default `3`) — maximum concurrent NNTP connections allowed from a single source IP address. Enforced in the daemon's accept loop before forking.
- `allow_plaintext_auth` (boolean, default `false`) — when `false` (default), `AUTHINFO` and `POST` on port 119 require `STARTTLS` first (`483` otherwise), matching the STARTTLS-enforcement design in the SSL / TLS section. When `true`, `AUTHINFO` and `POST` are permitted on unencrypted port-119 connections, for compatibility with older newsreaders that do not support `STARTTLS`. Enabling this exposes BinktermPHP account passwords to cleartext transmission for any client that does not negotiate TLS; the admin interface should surface this risk plainly (for example a warning shown when the setting is toggled on).

### Docker

Like the telnet and SSH daemons, the NNTP daemon runs as its own process rather than under Apache/PHP-FPM, so it needs its own considerations in the Docker packaging:

- **Port exposure** — `Dockerfile` `EXPOSE`s the daemon's `8119` / `8563`; the compose override maps host `119:8119` and `563:8563` so the container presents the standard ports.
- **Enable/disable at the container level** — Since the feature is disabled by default, the container's entrypoint/startup script needs to check the enable/disable setting before starting the `scripts/nntp_server.php` process, the same way other optional daemons are conditionally started. Toggling the setting through the admin interface should not require rebuilding the image, only restarting the daemon process.
- **Process supervision** — The daemon should be added to whatever process manager the container already uses to run the telnet/SSH daemons alongside Apache (e.g. supervisord), rather than introducing a new mechanism.

## Design Decisions

1. **Authentication required; subscribed areas only** — Anonymous access is not supported. Users must authenticate with their BinktermPHP credentials before any `LIST` or `GROUP` command is honored. The newsgroup list returned by `LIST ACTIVE` is filtered to the echoareas the authenticated user is subscribed to, so two users may see different sets of groups. Because authentication is a prerequisite for `LIST`/`GROUP` and, by default, `AUTHINFO` itself requires `STARTTLS` on port 119, a newsreader with no `STARTTLS` support has no usable access on port 119 unless the sysop has explicitly enabled `allow_plaintext_auth` (see decision 7) — or the client connects to port 563 instead.

2. **Flood control is configurable** — Per-user post rate limits (e.g. max posts per minute and per hour) should be configurable via the admin interface with reasonable defaults (e.g. 10 posts/minute, 60 posts/hour). Posts that exceed the limit are rejected with a 441 response rather than silently queued.

3. **No peering** — The server implements client-facing NNTP only. Server-to-server commands (`IHAVE`, `CHECK`, `TAKETHIS`) are not implemented. The BinktermPHP FTN mailer remains the sole mechanism for propagating messages to the wider network.

4. **Article expiry is a backend concern** — The NNTP daemon does not send `Expires:` headers and does not manage expiry itself. If the BinktermPHP backend prunes old echomail rows, those articles disappear from the newsgroup's `LOW`–`HIGH` range, but the article numbers they held are retired, never reissued (the per-area watermark does not roll back — see Article Numbering). Newsreaders that have already downloaded them will retain their local copies; requests for a retired or never-assigned article number return 423.

5. **Posting name policy enforced** — The `posting_name_policy` configured for the echoarea's network is enforced on inbound NNTP posts, exactly as it would be on a post submitted through the web interface.

6. **Message-ID collisions** — The constructed `Message-ID` folds in both the origin FTN address and the `MSGID` serial (see "Message-ID format"), so it is as unique as the underlying FTN identity. The remaining case is a genuine duplicate — the same message arriving over two feed paths — which is handled gracefully: the duplicate is logged and skipped; the existing article is not overwritten.

7. **Plaintext AUTHINFO is off by default** — On port 119, plaintext `AUTHINFO` (and `POST`) is disabled by default: the daemon returns `483` until the client completes `STARTTLS`. A sysop can explicitly enable it via the `allow_plaintext_auth` behavior setting for compatibility with legacy newsreaders that lack `STARTTLS`, accepting that account passwords are then transmitted in cleartext. Port 563 (implicit TLS) is always encrypted and is unaffected by this setting.

8. **Cross-posting via NNTP is capped independently** — Cross-posting through NNTP (a multi-group `Newsgroups:` header) is limited by a dedicated `max_cross_post_areas` setting (default `5`, matching the existing default), enforced in `NNTPPost` against the parsed `Newsgroups:` header before injection. A post that exceeds the limit is rejected with `441` rather than truncated to the first N groups. The setting is separate from the existing check of the same name because that enforcement lives in the web API route (`routes/api-routes.php`) — which both the web UI and the terminal composer post through, but the NNTP daemon does not — rather than in the shared `MessageHandler::postEchomail()` method. *Follow-up (not required for this proposal): moving `max_cross_post_areas` enforcement down into `postEchomail()` (or a helper it calls) would let all three paths — web, terminal, NNTP — share one implementation, consistent with the project's general preference for centralized validation logic.*

9. **Connection-level throttling is per-IP and pre-fork** — Concurrent connections from a single source IP are capped (default `3`, configurable via `max_connections_per_ip`), checked in the parent accept loop before a child is forked; excess attempts get a `400` response line and are closed immediately rather than queued. The cap is IP-scoped so it applies before authentication, unlike the per-user post rate limits. Per-session command-rate limiting is deferred as future work.

## Prior Art

- **ifgate / UUCP gateways** (1990s) — earliest FTN↔Usenet bridges, operated at the packet level
- **NewsGate** — a mid-90s Windows tool that bridged Fidonet echoareas to a local NNTP server
- **Synchronet BBS** — has a built-in NNTP server that serves its internal message bases; the architecture is similar to what is proposed here
- **MBSE BBS** — open-source FTN BBS with NNTP gateway support; its source is a useful reference for the header translation edge cases

## Summary

An NNTP interface for BinktermPHP is technically feasible and architecturally clean. The FTN ↔ NNTP data model mapping is good enough for practical use: echoareas become newsgroups, `MSGID`/`REPLY:` kludges become `Message-ID`/`References:` headers, and because BinktermPHP stores everything as UTF-8, there is no encoding gap to bridge. The main challenges are synthetic address construction for the `From:` header, Message-ID uniqueness for older messages without a `MSGID` kludge, and the write-path injection ensuring FTN protocol rules are respected when posting from a standard newsreader. A read-only implementation would be straightforward; full bidirectional posting adds meaningful complexity around authentication and abuse prevention.

If upstream NNTP peering is pursued as well, `docs/proposals/NNTPClientTransport.md` should be treated as the companion document. Shared concerns such as `Message-ID` construction, `From:` synthesis, header naming, and threading behavior should come from common code paths.
